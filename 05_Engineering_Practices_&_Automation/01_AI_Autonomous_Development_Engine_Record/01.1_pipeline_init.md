# 01.1 Learning from Working — 實機除錯經驗總結（含程式碼對照）

本文件記錄 01.1 Pipeline Initialization 從規劃稿到實機跑通過程中，遇到的 **12 個關鍵問題**。每個問題都附上**修改前（❌ 錯誤版）**與**修改後（✅ 正確版）**的程式碼片段對照，目的是讓未來新增技術棧、複製此架構到其他專案時，能直接辨識「這種寫法錯在哪」，不需要重新踩一次這些坑。

---

## 1. 倉庫名稱與規劃稿不一致

**問題**：規劃時命名 `heroic-ai-engine`，實際建立倉庫時用了 `ai-engine`，但 `.gitlab-ci.yml` 裡的下載網址沒有同步更新。

**現象**：`curl` 沒有報錯（`-f` 沒觸發），但下載下來的檔案是 0 bytes。

**❌ 修改前**

```bash
BASE_URL="http://10.0.0.10/ai-test/heroic-ai-engine/-/raw/${ENGINE_VERSION}"
```

**✅ 修改後**

```bash
BASE_URL="http://10.0.0.10/ai-test/ai-engine/-/raw/${ENGINE_VERSION}"
```

**教訓**：規劃文件裡的命名與實際操作要同步確認，尤其是貫穿多個檔案的倉庫名稱。

---

## 2. Private 倉庫下載未帶驗證 Token

**問題**：`ai-engine` 倉庫是 Private，`curl` 對 raw 檔案發請求時沒有帶身份驗證。

**現象**：GitLab 回傳 `302 Found`，導向登入頁 `/users/sign_in`，`curl -f` 不會偵測到這個失敗（302 不算 HTTP error），下載到的檔案是空內容。

**❌ 修改前**

```bash
curl -sf "${BASE_URL}/mcp_orchestrator.mjs" -o .agentic/runtime/mcp_orchestrator.mjs \
  || { echo "[-] 致命錯誤：無法下載引擎腳本"; exit 1; }
```

**✅ 修改後**

```bash
curl -sf --header "PRIVATE-TOKEN: ${PROJECT_ACCESS_TOKEN}" \
  "${BASE_URL}/mcp_orchestrator.mjs" -o .agentic/runtime/mcp_orchestrator.mjs \
  || { echo "[-] 致命錯誤：無法下載引擎腳本"; exit 1; }
```

**教訓**：Private 倉庫的 raw 檔案存取一定要帶驗證；判斷下載是否成功不能只靠 exit code，要實際檢查檔案大小或內容（可加 `ls -la` 除錯）。

## 3. npm 套件從未安裝就直接執行

**問題**：`.gitlab-ci.yml` 的 `script` 直接執行 `node`，但 `before_script` 從未跑過 `npm install`。

**現象**：`node` 指令執行後完全沒有任何 log 輸出，Pipeline 卻顯示 `Job succeeded`。

**❌ 修改前**

```yaml
before_script:
  - apt-get update && apt-get install -y curl git
  - mkdir -p .agentic/runtime
  - ENGINE_VERSION="v1.0.0"
  # 缺少 npm install
script:
  - node .agentic/runtime/mcp_orchestrator.js --tech-stack python
```

**✅ 修改後**

```yaml
before_script:
  - apt-get update && apt-get install -y curl git
  - npm install @modelcontextprotocol/sdk @google/genai
  - mkdir -p .agentic/runtime
  - ENGINE_VERSION="v1.0.0"
script:
  - node .agentic/runtime/mcp_orchestrator.mjs --tech-stack python
```

**教訓**："Job succeeded" 不代表程式真的執行了預期內容，務必加 echo/log 確認每個關鍵步驟真的有跑到。

## 4. tag 指向的 commit 內容語法不完整

**問題**：`v1.0.0` tag 是在某次貼上程式碼不完整時打的，導致檔案結尾缺少收尾括號。

**現象**：`SyntaxError: Unexpected end of input`，`main` 分支內容其實完整，只有 tag 指向的舊 commit 是壞的。

**❌ 修改前（tag 指向的舊版本結尾）**

```javascript
run().catch(err => {
    console.error("[-] 未預期錯誤:", err);
    process.exit(1);
// 缺少 }); 收尾，檔案在此截斷
```

**✅ 修改後（重新打 tag 指向完整版本）**

```javascript
run().catch(err => {
    console.error("[-] 未預期錯誤:", err);
    process.exit(1);
});
```

```bash
# 重新打 tag 的指令
git tag -d v1.0.0
git push origin :refs/tags/v1.0.0
git tag v1.0.0
git push origin v1.0.0
```

**教訓**：tag 是固定指向某個 commit、不會自動跟著分支移動；修改原始碼後若 tag 已存在，必須重新打 tag 才會生效。

## 5. MCP SDK 套件名稱錯誤（不存在的套件）

**問題**：使用 `@modelcontextprotocol/client`，這是尚未發布的 SDK 2.0 拆分套件命名。

**現象**：`Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: No "exports" main defined in .../client/package.json`

**❌ 修改前**

```javascript
const { McpClient } = require("@modelcontextprotocol/client");
const { GoogleGenAI } = require("@google/genai");

const mcpClient = new McpClient();
await mcpClient.connect(mcpConfig);
```

**✅ 修改後**

```javascript
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";
import { GoogleGenAI } from "@google/genai";

const mcpClient = new Client({ name: "heroic-ai-orchestrator", version: "1.0.0" });
await mcpClient.connect(transport);
```

**教訓**：套件名稱必須實際查證 npm 官方頁面確認存在且為穩定版，不能憑記憶或文件片段直接假設；連帶地 Client 的初始化方式（要搭配 `StdioClientTransport`）也跟著改變，不是單純換個 import 路徑而已。

## 6. CommonJS 與 ESM 模組系統混用

**問題**：套件換成 `@modelcontextprotocol/sdk` 後，引入語法改成 `import`，但檔案副檔名仍是 `.js`。

**現象**：`SyntaxError: Cannot use import statement outside a module`

**❌ 修改前**

```javascript
// 檔名: mcp_orchestrator.js
const { McpClient } = require("@modelcontextprotocol/client");
const fs = require("fs");
const path = require("path");
```

**✅ 修改後**

```javascript
// 檔名: mcp_orchestrator.mjs
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import fs from "fs";
import path from "path";
```

```yaml
# .gitlab-ci.yml 對應修改
- curl ... -o .agentic/runtime/mcp_orchestrator.mjs   # 改副檔名
script:
  - node .agentic/runtime/mcp_orchestrator.mjs --tech-stack python  # 改副檔名
```

**教訓**：改變 import 語法的同時，要檢查模組系統是否一致；`.mjs` 是不需要額外設定檔（如 `package.json` 的 `"type": "module"`）的最簡單做法，但 CI 腳本裡所有引用該檔名的地方都要同步修改。

## 7. YAML 語法錯誤（冒號與特殊字元）

**問題**：除錯用的 echo 字串裡帶有冒號。

**現象**：`Unable to create pipeline` / `yaml invalid`，`jobs:ai_pipeline_init:script config should be a string`，Pipeline 連建立都失敗（顯示 0 jobs）。

**❌ 修改前**

```yaml
script:
  - echo "=== node 執行結束，exit code: $? ==="
```

**✅ 修改後**

```yaml
script:
  - echo "node 執行結束"
```

**教訓**：YAML 對冒號等特殊字元敏感，echo 訊息盡量用純文字；發現 `0 jobs` 或 `yaml invalid` 要先去 commit 頁面確認 `.gitlab-ci.yml` 語法本身有沒有問題，而非直接懷疑程式邏輯。

## 8. GitLab MCP Server 套件已停止維護，schema 不相容

**問題**：使用官方 `@modelcontextprotocol/server-gitlab`，已停止維護（最後更新 2025.4.25）。

**現象**：先是 `GITLAB_PERSONAL_ACCESS_TOKEN environment variable is not set`，換對變數名後又出現 `ZodError: invalid_value ... expected "object"`。

**❌ 修改前**

```javascript
const transport = new StdioClientTransport({
    command: "npx",
    args: ["-y", "@modelcontextprotocol/server-gitlab"],
    env: {
        GITLAB_API_URL:       config.gitlabUrl,
        GITLAB_PRIVATE_TOKEN: config.gitlabToken,
    }
});

const ALLOWED_TOOLS = new Set([
    "gitlab_get_issue",
    "gitlab_list_issues",
    "gitlab_create_issue_comment",
    "filesystem_list_directory",
    "filesystem_read_file",
    "filesystem_get_file_info"
]);
```

**✅ 修改後**

```javascript
const transport = new StdioClientTransport({
    command: "npx",
    args: ["-y", "@ttpears/gitlab-mcp-server"],
    env: {
        ...process.env,
        GITLAB_URL:   config.gitlabUrl.replace(/\/api\/v4\/?$/, ""),
        GITLAB_TOKEN: config.gitlabToken,
    }
});

const ALLOWED_TOOLS = new Set([
    "get_issues",
    "get_notes",
    "create_note",
    "browse_repository",
    "get_file_content",
]);
```

**教訓**：採用第三方 MCP Server 套件前，先確認其維護狀態（npm 頁面的 deprecated 警告、最後更新時間）；換套件不只是換 `args`，連環境變數命名、工具名稱命名空間都會整套改變。

## 9. MCP Tool Schema 格式與 Gemini API 格式不相容

**問題**：MCP 協定的 tool 物件包含 `title`、`inputSchema`、`annotations` 等欄位，直接把整個物件丟給 Gemini。

**現象**：`Unknown name "title" at 'tools[0].function_declarations[0]': Cannot find field.`（`inputSchema`、`annotations` 同理報錯）

**❌ 修改前**

```javascript
const { tools: mcpTools } = await mcpClient.listTools();
const filteredTools = mcpTools.filter(t => ALLOWED_TOOLS.has(t.name));

// 直接把 MCP 原始格式丟給 Gemini
const response = await aiClient.models.generateContent({
    model: "gemini-2.5-flash",
    contents: conversationHistory,
    config: {
        systemInstruction,
        tools: [{ functionDeclarations: filteredTools }]  // ← 含 title/inputSchema/annotations
    }
});
```

**✅ 修改後**

```javascript
function toGeminiFunctionDeclaration(mcpTool) {
    const { name, description, inputSchema } = mcpTool;
    return {
        name,
        description: description || mcpTool.title || name,
        parameters: stripUnsupportedSchemaFields(inputSchema) || { type: "object", properties: {} }
    };
}

function stripUnsupportedSchemaFields(schema) {
    if (!schema || typeof schema !== "object") return schema;
    const UNSUPPORTED_KEYS = new Set(["additionalProperties", "$schema", "title", "default"]);
    const cleaned = {};
    for (const [key, value] of Object.entries(schema)) {
        if (UNSUPPORTED_KEYS.has(key)) continue;
        if (key === "properties" && typeof value === "object") {
            cleaned.properties = Object.fromEntries(
                Object.entries(value).map(([k, v]) => [k, stripUnsupportedSchemaFields(v)])
            );
        } else if (key === "items") {
            cleaned.items = stripUnsupportedSchemaFields(value);
        } else {
            cleaned[key] = value;
        }
    }
    return cleaned;
}

const filteredTools = mcpTools
    .filter(t => ALLOWED_TOOLS.has(t.name))
    .map(toGeminiFunctionDeclaration);   // ← 轉換成 name/description/parameters
```

**教訓**：不同協定（MCP）與不同 API（Gemini function calling）的 schema 格式不能直接互通，跨系統介接時要有明確的格式轉換層，不能假設「反正都是 JSON 物件就能直接傳」。

## 10. 跨專案路徑混淆（Issue Tracker vs 程式碼倉庫）

**問題**：只給 Gemini 一個 `projectPath`，沒有區分「Issue 在哪個專案」跟「程式碼在哪個專案」。

**現象**：Gemini 自行瞎猜格式（`"project 21"`、`"Agentic/project-21"`），或在錯誤的倉庫裡找檔案。

**❌ 修改前**

```javascript
const projectPath = await resolveProjectPath(config);

const systemInstruction = `
【你的核心任務】：
1. 調用 get_issues 工具讀取專案的 Issue ${issueIid} 詳細內容。
   - projectPath 參數必須使用這個精確值："${projectPath}"
2. 調用 browse_repository 工具盤點工作目錄下的檔案拓撲結構。
   // ← 沒有指定 projectPath，Gemini 用了上面同一個 projectPath（Issue Tracker），
   //   結果在錯誤的倉庫裡找檔案
3. 調用 get_file_content 工具讀取 .agentic/instructions.md 與 .agentic/architecture_rules.md。
`;
```

**✅ 修改後**

```javascript
const issueTrackerPath = await resolveProjectPath(config);        // 查 GitLab API
const codeRepoPath = process.env.CI_PROJECT_PATH;                  // GitLab CI 內建變數

const systemInstruction = `
【重要：本次任務涉及兩個不同的 GitLab 專案，絕對不可混用】

A. Issue Tracker 專案路徑（用於讀取需求與貼留言）："${issueTrackerPath}"
   - 僅能在調用 get_issues、get_notes、create_note 時使用此路徑

B. 程式碼倉庫路徑（用於盤點檔案與讀取韁繩規範）："${codeRepoPath}"
   - 僅能在調用 browse_repository、get_file_content 時使用此路徑

【你的核心任務】：
1. 調用 get_issues 工具讀取 Issue ${issueIid} 詳細內容（projectPath 用 A："${issueTrackerPath}"）。
2. 調用 browse_repository 工具盤點程式碼倉庫的檔案拓撲結構（projectPath 用 B："${codeRepoPath}"）。
3. 調用 get_file_content 工具讀取 .agentic/instructions.md（projectPath 用 B："${codeRepoPath}"）。
`;
```

**教訓**：當架構涉及多個 GitLab 專案時，絕對不能讓 LLM 自己猜測或合併路徑概念，必須由程式明確查出並逐一指定，且要在每個任務步驟上重複標註該用哪一個。

## 11. Issue IID 依賴錯誤的 GitLab 內建變數

**問題**：`ISSUE_IID` 依賴 `$CI_EXTERNAL_ISSUE_IID`，這個內建變數只在 Pipeline 被 Issue 事件**直接**觸發時才存在；本架構是透過 Trigger API 跨專案觸發，該變數始終是空的。

**現象**：`[-] 致命錯誤: 缺少必要環境變數: issueIid`

**❌ 修改前**

```yaml
# .gitlab-ci.yml
variables:
  ISSUE_IID: "$CI_EXTERNAL_ISSUE_IID"   # ← Trigger API 觸發時這個變數不存在
```

```javascript
// mcp_orchestrator.mjs
const config = {
    issueIid: process.env.ISSUE_IID,   // ← 永遠是 undefined
    // ...
};
```

**✅ 修改後**

```yaml
# .gitlab-ci.yml
# ISSUE_IID 整行移除，不再需要
```

```javascript
// mcp_orchestrator.mjs
async function resolveTargetIssueIid(config) {
    const url = `${config.gitlabUrl}/projects/${config.projectId}/issues` +
                `?labels=agent::enable&state=opened&order_by=updated_at&sort=desc&per_page=1`;

    const res = await fetch(url, { headers: { "PRIVATE-TOKEN": config.gitlabToken } });
    const issues = await res.json();
    return issues[0].iid;   // 主動查詢取代被動接收
}
```

**教訓**：跨專案的 Trigger API 觸發方式，無法取得原始 Webhook 事件的完整 payload（如 issue.iid），設計階段就要確認哪些資訊在新架構下會「消失」，並改用主動查詢取代被動接收。

## 12. Webhook 重複觸發導致同一專案產出兩份報告

**問題**：GitLab 對「先建立 Issue（無標籤）、之後再打標籤」會分別送出 `open` 與 `update` 兩個獨立 webhook 事件；GitLab webhook 原生沒有依標籤過濾的機制。

**現象**：同一個 Issue 出現 4 則留言（前端 2 則 + 後端 2 則）；第一版去重邏輯的 marker 字串沒有區分技術棧，導致前端被後端的留言誤判為「已存在」而錯誤跳過。

**❌ 修改前（完全沒有去重機制）**

```javascript
async function run() {
    const issueIid = await resolveTargetIssueIid(config);
    const issueTrackerPath = await resolveProjectPath(config);
    // 直接往下連 MCP、呼叫 Gemini，沒有檢查是否已處理過
    const transport = new StdioClientTransport({ /* ... */ });
    // ...
}
```

**❌ 修改後第一版（marker 字串沒有區分技術棧，仍會誤判）**

```javascript
async function hasExistingSpecDraft(config, issueIid, techStack) {
    // ...
    const marker = `Spec Draft - Issue #${issueIid}`;   // ← 前後端標題都含這段，無法區分
    return notes.some(note => (note.body || "").includes(marker));
}
```

```javascript
// system prompt 標題也沒有技術棧標記
# 🔍 Spec Draft - Issue #${issueIid}
```

**✅ 修改後最終版（marker 帶上 techStack）**

```javascript
async function hasExistingSpecDraft(config, issueIid, techStack) {
    const url = `${config.gitlabUrl}/projects/${config.projectId}` +
                `/issues/${issueIid}/notes?sort=desc&order_by=created_at&per_page=20`;
    const res = await fetch(url, { headers: { "PRIVATE-TOKEN": config.gitlabToken } });
    const notes = await res.json();

    const marker = `Spec Draft - Issue #${issueIid} [${techStack}]`;   // ← 加上技術棧區分
    return notes.some(note => (note.body || "").includes(marker));
}

async function run() {
    const issueIid = await resolveTargetIssueIid(config);

    const alreadyProcessed = await hasExistingSpecDraft(config, issueIid, techStack);
    if (alreadyProcessed) {
        console.log(`[*] Issue #${issueIid} 已存在 Spec Draft 留言，本次跳過不重新執行`);
        return;   // ← 在連 MCP、呼叫 Gemini 之前就攔截
    }
    // ... 才繼續往下執行
}
```

```javascript
// system prompt 標題同步加上技術棧標記
# 🔍 Spec Draft - Issue #${issueIid} [${techStack}]
```

**教訓**：webhook 重複觸發是平台層級的已知限制，業界標準解法是在程式內做冪等性（idempotent）處理，而非試圖在 webhook 層攔截；當多個獨立 Pipeline 共用同一份資料來源（同一個 Issue Tracker）時，去重判斷的識別字串必須帶上能區分「誰」的維度，否則會互相誤判——這也是為什麼「加上去重檢查」跟「去重檢查寫對」是兩件事，第一版加了機制但 marker 設計有漏洞，依然會出錯。

## 總結：問題類型分布

| 類型        | 對應問題編號  | 共通教訓                                                              |
| --------- | ------- | ----------------------------------------------------------------- |
| 設定與規劃稿不一致 | 1       | 命名統一性需要貫穿所有檔案核對                                                   |
| 認證與權限     | 2       | Private 資源存取要主動驗證，不能假設預設可讀                                        |
| CI 腳本基本功  | 3、7     | 缺少安裝步驟、YAML 特殊字元都會導致難以察覺的靜默失敗                                     |
| 版本管理      | 4       | tag 不會自動跟隨分支更新，修改後要重新打 tag                                        |
| 套件選用與相容性  | 5、6、8、9 | 套件名稱、模組系統、維護狀態、schema 格式都要逐一查證，不能假設「看起來像」就是對的                     |
| 架構設計缺口    | 10、11   | 多專案、跨系統觸發的架構，要明確設計「誰該知道什麼」，不能讓 LLM 自行猜測或依賴可能不存在的變數                |
| 平台限制與冪等性  | 12      | webhook 重複觸發是平台限制非設計錯誤；去重機制的識別鍵設計要考慮「跨資源共用同一份資料來源」的情境，加了機制不代表設計正確 |
