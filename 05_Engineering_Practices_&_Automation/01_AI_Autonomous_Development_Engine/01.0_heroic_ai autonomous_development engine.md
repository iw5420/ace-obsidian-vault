# Heroic AI 全自動化開發引擎 — 核心索引與主控清單（Manifest）v2

> **版本說明**：本版本（v2）為架構重構版，目的是把原本綁定「政府標案爬蟲（Python/FastAPI + React）」單一專案的流水線，**抽象成可套用於任何全端專案的通用框架**。重構依據三項已確認的設計決策（詳見文末「v1 → v2 變更紀錄」）：
> 
> 1. Phase 1 已改為 Gemini + MCP 驅動的盤點與規格起草，原本獨立的「技術能力檢索」階段內容與其高度重疊，故合併。
> 2. 「Codebase 語意檢索」在業界（GitLab Developer Flow、Claude Code 官方 GitLab CI/CD 文件、Upsun 自建 Agent 等案例）並非獨立的、對外可見的 GitLab 狀態階段，而是 Agent 動手前的內部自我檢核，故降階為 **Skill**，由 Claude Code 在 Phase 3 開工前主動調用，平時對人類無感、只在發現落差時才浮現。
> 3. 技術棧（Python/FastAPI、React、Java、Node…）相關內容全面參數化，透過 `.agentic/project.yml` 宣告，流水線文件本身不再寫死任何特定語言或框架。

依循 **Harness Engineering（駕馭馬匹的韁繩工程學）** 規範，旨在消滅 Vibe Coding，透過明確的階層化柵欄（Layered Guardrails）與環境沙盒化機制，建立人機協同、意圖驅動的企業級自動化流水線。

## 🎯 0. 設計原則（新增）

|原則|說明|
|---|---|
|**技術棧無關（Stack-Agnostic）**|流水線文件（01.x）只定義「流程」，不定義「語言/框架細節」。語言細節下放到各業務倉庫的 `.agentic/instructions.md` 與 `.agentic/architecture_rules.md`，由 `.agentic/project.yml` 宣告要套用哪一份。|
|**狀態機只反映人機交握點**|GitLab 標籤（`status::*`）只在「需要人類決策、或需要對外稽核」時才出現。Agent 內部的自我檢核、子任務拆解，一律歸類為 Skill，不佔用獨立 Phase 與標籤。|
|**Generator-Critic 異質校驗**|凡是「生成」與「校驗」同一份產出的兩個動作，一律由不同模型擔任（Gemini 生成 Spec/PLAN，Claude Code 實作前用自己的檢索能力校驗 PLAN 是否落地可行；Claude Code 寫代碼，Gemini 審代碼）。同一模型不審自己的作業。|
|**唯讀沙盒化優先**|任何 Agent 在「分析/校驗」性質的階段，工具存取一律白名單限制為唯讀，寫入動作（commit、貼留言、改標籤）集中在明確定義的單一出口，方便稽核與回滾。|
|**版本 Pinning**|任何中央共用引擎（`ai-engine`）的更新，業務倉庫一律以明確 tag 引用，禁止追 `main`，升級是顯性人類決策。|

## 🏗️ 1. 系統拓撲與工具分工（Topology & Component Roles）

|角色層級|負責工具|運作環境|核心任務|
|---|---|---|---|
|**大腦與狀態機**|GitLab Issue & MR|GitLab 伺服器|控管生命週期、標籤流轉、記錄人類決策與稽核軌跡。|
|**規格與評審員（Critic）**|Gemini（依 `project.yml` 指定模型版本）|CI Pipeline 容器內（MCP stdio 子行程，無常駐服務、不開 port）|長文本/批次唯讀任務：Spec Draft 起草、PLAN.md 生成、MR Diff 靜態審查。|
|**程式碼馬車夫（Driver）**|Claude Code|本地宿主機（CLI，OS 不限）|本地高效執行：讀取 Codebase、調用本地 Skill 自我校驗、撰寫 TDD 測試與實作。|
|**安全執行沙盒（Sandbox）**|Docker 容器（image 依 `project.yml` 之 `sandbox_image` 決定）|宿主機 Docker|隔離執行環境，依技術棧編譯/測試（`pytest`／`jest`／`mvn test`…），阻絕 AI 弄髒宿主機環境。|

> **角色分工的理由（沿用 v1 已驗證之決策）**：Phase 1（盤點/起草）與 Phase 4（MR Review）用 Gemini，理由是成本控制（唯讀批次任務適合低成本模型）與專家分工（Claude Code 額度保留給 Phase 3 本地 TDD 執行，那是它最具優勢、需要多輪工具調用穩定性的場景）。

## 📐 2. 專案組態檔（新增，是達成「跨專案複用」的關鍵機制）

每個業務倉庫根目錄須有 `.agentic/project.yml`，宣告該倉庫的技術棧與環境參數，流水線腳本（`mcp_orchestrator.mjs`、CI YAML、Skill）一律讀此檔案動態決定行為，**不寫死任何特定語言**：

```yaml
# .agentic/project.yml
tech_stack: python            # python | react | java | node | vue | go ...
layer_convention: router-service-repository   # 或 mvc / feature-based / clean-architecture
test_runner: pytest           # pytest | jest | junit | go test ...
sandbox_image: python:3.11-slim
issue_tracker_mode: separate  # separate（獨立 Issue Tracker 倉庫）｜ embedded（本倉庫自己的 Issues）
issue_tracker_project_id: 123 # issue_tracker_mode=separate 時填寫
gemini_model: gemini-3.1-flash-lite   # 依額度與正式/測試環境調整
max_retry: 5                  # Phase 3 自我修正上限
```

新專案要套用本框架時，**只需要**：

1. 建立/指向一個 Issue Tracker（可獨立倉庫，也可用自己倉庫的 Issues）。
2. 在各業務倉庫放入 `.agentic/project.yml` + 對應技術棧的 `instructions.md` / `architecture_rules.md`。
3. 設定 CI/CD Variables 與 Webhook（見第 6 節）。

完全不需要修改 01.x 流水線文件本身——這就是「同一套規範套用到不同全端專案」的實作方式。

## 🔄 3. 流水線生命週期與韁繩文件映射（Pipeline Lifecycle）

本流水線由有限狀態機（FSM）驅動。**相較 v1，階段數從 7 個精簡為 5 個**，被精簡掉的「技術能力檢索」已轉化為 Phase 3 內部調用的 Skill（見第 4 節）。

### Phase 1：流水線初始化與 AI 規格起草（Pipeline Init & Spec Drafting）

- **對應檔案：** [01.1_pipeline_init.md]
- **觸發條件：** Issue Tracker 開出 Issue 並打上標籤 `agent::enable`。
- **系統標籤：** `status::analyzing`（執行中）
- **執行者：** Gemini，透過 MCP 工具鏈（白名單唯讀：`get_issues`、`get_notes`、`browse_repository`、`get_file_content`，唯一寫入動作為 `create_note`）。
- **核心任務：**
    1. 主動查詢符合條件的最新 Issue（不依賴 CI 內建變數），去重檢查避免重複觸發。
    2. 讀取目標業務倉庫的 `.agentic/project.yml` 與對應技術棧的 `instructions.md`、`architecture_rules.md`。
    3. 對 Codebase 進行語意化檢索與架構規範比對，**一次性**產出整合「需求意圖、技術選型、模組設計、檔案拓撲、架構風險評估」的 **Spec Draft**，貼回 Issue 留言，標題帶 `[tech_stack]` 標記。
- **Context 注入範疇：** [01.1_pipeline_init.md]+ Issue 原始文本 + `.agentic/project.yml` + 對應韁繩文件。
- **產出與下一步：** 人類審閱 Spec Draft，回覆 `Approved` 後流轉至 Phase 2。

> ⚠️ v1 中原本獨立的「技術能力檢索與範疇界定」（舊 Phase 2 / `01.2_skill_search.md`）內容已併入本階段，因為 Gemini 在此階段本就握有 Codebase 唯讀工具，沒有理由拆成兩個分開觸發、分開審查的階段。

### Phase 2：結構化計畫書生成與人機對齊（Structured Planning & Human Alignment）

- **對應檔案：** [01.2_planning.md]
- **觸發條件：** 人類在 Issue 回覆 `Approved`。
- **系統標籤：** `status::waiting-human-plan-approval`
- **執行者：** Gemini。
- **核心任務：** 依 Phase 1 的 Spec Draft 生成結構化 **PLAN.md**（明確定義功能目標、API/介面契約變更、UI 調整、測試項目、Schema 變更——內容依 `tech_stack` 套用對應範本），推送到 Issue 留言等待人類最終審查。人類回覆確認後自動開闢分支，並將 PLAN.md commit 至分支根目錄。
- **Context 注入範疇：** [01.2_planning.md] + Phase 1 之 Spec Draft。

### Phase 3：本地驅動執行與沙盒自我修正（Local TDD Execution & Sandbox Self-Correction）

- **對應檔案：** [01.3_tdd_execute_and_sandbox_self_correct.md]
- **觸發條件：** 分支建立完成，PLAN.md 已就位。
- **系統標籤：** `status::executing` / `status::blocked`（中斷時）
- **執行者：** Claude Code，本地宿主機 CLI。
- **核心任務：**
    1. **【開工前置動作，內部 Skill，平時對人類無感】** 調用 [skills/feasibility_check.md]：讀取分支內 PLAN.md，與**當下真實 Codebase**做交叉校驗（Explore/Plan 子任務），確認 Gemini 在 Phase 1 的盤點結論此刻仍然成立。
        - **校驗通過** → 靜默接續下一步，不產生任何 GitLab 可見紀錄。
        - **發現落差**（例如 PLAN.md 假設的檔案已不存在、依賴版本衝突、架構柵欄會被打破）→ 立即中止，貼留言說明落差並標記 `status::blocked`，交還人類或 Gemini 重新對齊，**不允許自行猜測修正 PLAN.md**。
    2. 校驗通過後，透過 `docker exec` 將依賴安裝、測試執行限縮在 `project.yml` 指定的沙盒容器內。
    3. 嚴格 Test-First：先寫測試，再寫實作。
- **自我修正極限：** `max_retry`（預設 5，可於 `project.yml` 覆寫）。超限則 `status::blocked` 並退出。
- **Context 注入範疇：** [01.3_tdd_execute_and_sandbox_self_correct.md] + 分支出口之 PLAN.md + [skills/feasibility_check.md]。

### Phase 4：代碼評審與 Generator-Critic 驗證（Code Review）

- **對應檔案：** [01.4_code_review.md]
- **系統標籤：** `status::review-failed`（審查未通過時）
- **執行者：** Gemini（扮演 Critic）。
- **核心任務：** Claude Code 完成實作後執行 Git Push 並建立 MR。觸發 Gemini 調用 MR Diff API，嚴格對照該分支之 PLAN.md、`.agentic/architecture_rules.md` 與通用 Clean Code 規範，進行線上行內程式碼質疑（Discussions）。
- **Context 注入範疇：** [01.4_code_review.md] + PLAN.md + MR Diff 文本。

### Phase 5：結晶化與自動化收尾（Crystallize & Finalize）

- **對應檔案：** [01.5_crystallize_and_final.md]
- **核心任務：** 人類最終核可 MR 並 Merge。Webhook 觸發收尾腳本，關閉 Issue。Gemini 讀取變更，自動生成符合語意化版本（Semantic Versioning）的 **CHANGELOG.md**。
- **Context 注入範疇：** [01.5_crystallize_and_final.md] + 最終合併之 Commit 紀錄。

## 🧩 4. Skill 庫（新增章節）

Skill 與 Phase 不同：Skill **不對應 GitLab 狀態標籤**，是 Agent（目前僅 Claude Code 會用到）在執行任務過程中，依需要主動調用的可重用、可版本控管的內部工序。Skill 一律放在 `skills/` 目錄下，**不參與 01.x 流水線編號**，可被任何 Phase 引用，也可跨技術棧複用。

| Skill 檔案                      | 調用者         | 調用時機        | 功能                                      |
| ----------------------------- | ----------- | ----------- | --------------------------------------- |
| [skills/feasibility_check.md] | Claude Code | Phase 3 開工前 | 對照 PLAN.md 與當下真實 Codebase，校驗落地可行性，異常才上報 |

> 未來若有其他可重用的內部工序（例如「依賴升級影響分析」「資料庫遷移腳本生成」），一律以此模式擴充 `skills/` 目錄，不要再回頭把它們做成獨立的 GitLab Phase。

## 🛠️ 5. 環境基礎建設要求（Infrastructure Prerequisites）

詳細部署腳本參閱 [01.5_crystallize_and_final.md] 附錄。

### 5.1 倉庫拓撲（依 `issue_tracker_mode` 彈性決定）

**模式 A（`separate`，適合前後端分離、多業務倉庫共用同一需求池）：**

```
ai-engine/                      # 中央共用引擎倉庫（Private，版本 Pinning）
├── mcp_config.json
└── mcp_orchestrator.mjs

<issue-tracker-repo>/           # 純 Issue Tracker，不存放程式碼

<business-repo-A>/              # 例：frontend
├── .agentic/
│   ├── project.yml
│   ├── instructions.md
│   ├── architecture_rules.md
│   └── runtime/                # CI 執行期暫存（.gitignore）
└── （現有程式碼）

<business-repo-B>/              # 例：backend，結構同上
```

**模式 B（`embedded`，適合單一全端 monorepo 或小型專案）：**

```
<project-repo>/
├── .agentic/
│   ├── project.yml             # issue_tracker_mode: embedded
│   ├── instructions.md
│   ├── architecture_rules.md
│   └── runtime/
└── （前後端程式碼，依 project.yml 的 layer_convention 分層）
```

### 5.2 韁繩配置（`.agentic/`）

- **instructions.md**：定義該倉庫技術棧規範（語言版本、框架、強型態/Lint 要求、測試框架）。
- **architecture_rules.md**：定義分層依賴柵欄（例如 Router→Service→Repository、禁止循環匯入、禁止跨層越權調用）。內容依 `layer_convention` 撰寫。

### 5.3 常駐 Docker 開發沙盒

```bash
docker run -d --name <project>-dev-sandbox \
  -v <host-path>:/workspace \
  -w /workspace \
  -e PYTHONPATH=/workspace \
  <project.yml 指定之 sandbox_image> tail -f /dev/null
```

> 若涉及瀏覽器自動化（如爬蟲），沙盒內需預裝對應依賴（Playwright/Chromium 等），於 `project.yml` 額外宣告 `sandbox_extra_deps`。

## 📋 6. 狀態標籤總覽（State Machine Summary）

|標籤|出現於|意義|
|---|---|---|
|`agent::enable`|人類手動打標|觸發 Phase 1|
|`status::analyzing`|Phase 1 執行中|Gemini 正在起草 Spec Draft|
|`status::waiting-human-plan-approval`|Phase 2|等待人類核准 PLAN.md|
|`status::executing`|Phase 3|Claude Code 正在執行 TDD 循環|
|`status::blocked`|Phase 3|自我修正超限，或 Skill 校驗發現落差|
|`status::review-failed`|Phase 4|Gemini Critic 審查未通過|
|（無標籤，MR 狀態代管）|Phase 5|等待人類 Merge|
