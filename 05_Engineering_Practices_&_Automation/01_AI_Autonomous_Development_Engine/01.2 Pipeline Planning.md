# 01.2 Pipeline Planning & Human Alignment（結構化計畫書生成與人機對齊）— 實作規範 v1

本文件定義 **Heroic AI 全自動化開發引擎** 的 Phase 2 實作規範，銜接 [01.1_pipeline_init.md](https://claude.ai/chat/01.1_pipeline_init.md) 產出的 Spec Draft。本版本比照 01.1 的撰寫風格，**每一節都明確標出「現在要做什麼」「怎麼操作」「會產生什麼結果」**，可直接照本文件操作與除錯。

> **唯一權威性聲明**：本文件附錄 B 定義的 `PLAN.md` 範本，是全流水線**唯一**的計畫書格式來源。Phase 3（TDD 執行）、Phase 4（Code Review）、Phase 5（結晶化收尾）一律**讀取、引用**本節範本產出的檔案，不得各自定義或衍生第二份格式。

---

## 🗺️ 0. 這個階段在解決什麼問題

Phase 1 結束時，Issue 留言區會躺著一到多份 Spec Draft（依技術棧各一份，標題帶 `[react]` / `[python]` 等標記）。**Spec Draft 是分析報告，不是可執行的施工藍圖**。Phase 2 要做的事，是把「人類核准過的 Spec Draft」轉換成「結構固定、Claude Code 可以直接拿來對照施工的 PLAN.md」，並把它**實體 commit 進一個全新分支**，作為後續所有階段的唯一依據文件。

**現在要做什麼**：在 Issue 留言回覆，把 Spec Draft 對齊到你要的樣子。 **怎麼操作**：直接打字回覆，像在跟同事討論規格一樣，不需要特殊語法。 **會產生什麼結果**：Gemini 讀到留言後，會在同一個 Issue 重新貼一版 PLAN.md 草稿，迴圈直到你回覆 `Approved`，才會真的建立分支、寫入檔案。

## 🔄 1. 觸發機制（與 01.1 共用同一條 Webhook，新增一種事件）

Phase 1 的 Webhook 只勾選了 `Issue events`。Phase 2 需要監聽**留言事件**才能知道你什麼時候回覆、什麼時候回覆了 `Approved`，因此本階段要求在原本兩條 Webhook 上**額外勾選**：

```
前往 gov-tender-fetcher 倉庫 → Settings → Webhooks → 編輯既有兩條 Webhook
勾選：☑ Comment events（GitLab 介面顯示為 "Note events"）
```

> ⚠️ **不需要新增第三條 Webhook**，沿用 01.1 已設定好的兩條（分別指向前端、後端 Trigger API），只是讓它們也對留言事件敏感。這樣同一條 Pipeline 內可以用不同 stage 處理 Phase 1（Issue 開啟/更新觸發）與 Phase 2（留言觸發），不需要拆成兩個獨立專案。

**現在要做什麼**：手動到 Webhook 設定頁勾選 Comment events（一次性，兩條都要勾）。 **怎麼操作**：照上面路徑點擊，Save 即可。 **會產生什麼結果**：之後每次有人在 Issue 下方留言（不限於 `Approved`），都會觸發一次 Pipeline，由 Pipeline 內部邏輯自行判斷該不該動作（見第 3 節去重與狀態判斷）。

## 🔄 2. 每次使用流程（日常操作）

> ⚠️ **前提聲明**：以下流程是**完成第 3、4 節的部署動作之後**才會有的行為。還沒部署完，現在去留言不會有反應。建議先跳去看第 3、4 節，部署完成後再回來當速查表。

**你要做的事只有一件**：在 Issue 下方打字回覆，滿意就回 `Approved`，不滿意就直接寫想法，不需要任何特殊語法。

接下來分兩種情境說明回覆之後會發生什麼事：

### 情境一：你還不滿意，給了修正意見

例如你回覆：「後端不要新增 trigger 端點，前端改用排程觸發」。

1. Webhook 偵測到這則留言（Comment events），觸發前後端兩條 Pipeline 的 `plan` stage。
2. Pipeline 內部判斷：這則留言是你寫的、內容不是 `Approved`、且 Issue 上已經有 Spec Draft → 判定為「該處理」。
3. Gemini 讀取你這則留言＋目前最新版 PLAN.md 草稿，重新生成一版，貼回 Issue。
4. 你看到新草稿，繼續回覆意見或直接核准——重複幾輪都可以，沒有次數限制。

### 情境二：你核准了

你回覆精確字串 `Approved`。

1. Webhook 偵測到留言，觸發 `plan` stage。
2. Pipeline 判斷這是核准動作 → 建立分支 `feature/issue-{IID}`。
3. 將最終版 PLAN.md commit 進分支根目錄（`.agentic/PLAN.md`）。
4. Issue 標籤由 `status::waiting-human-plan-approval` 轉為 `status::executing`。
5. Issue 留言確認：「已建立分支 feature/issue-101，PLAN.md 已就位，Phase 3 即將開始」。

> 兩種情境的等待時間都約 30 秒～1 分鐘（比 Phase 1 快，因為 Gemini 只需重新生成結構化文件，不需要重新盤點整個 Codebase）。

## 🛠️ 3. 容器內自動執行細節（含：你需要動手改 `mcp_orchestrator.mjs` 的部分）

> 本節大部分內容是 Pipeline 內部自動發生的事，讀者不需要手動執行任何指令；**但本節開頭的兩件事是例外，需要你實際動手修改 `ai-engine` 倉庫裡的原始碼**，請特別注意標示。

### ✋ 動手事項一：原本的 `mcp_orchestrator.mjs` 還不認得 `--phase` 參數

01.1 第 6 節貼出的 `mcp_orchestrator.mjs`，CLI 只解析 `--tech-stack`，沒有 `--phase`。第 4 節的 `.gitlab-ci.yml` 卻已經在呼叫 `--phase planning`，所以**這份檔案如果不改，Phase 2 完全不會動作**。

**現在要做什麼**：打開 `ai-engine` 倉庫的 `mcp_orchestrator.mjs`，找到解析 CLI 參數與 `main()` 函式的地方。 **怎麼操作**：在參數解析處新增 `--phase` 旗標（預設值 `init`，維持向下相容，不會影響既有 Phase 1 的呼叫方式），並在 `main()` 內依此值分流：

```javascript
// 在既有的 CLI 參數解析區塊新增
const phase = args.phase || "init";   // 預設 init，向下相容 01.1 既有呼叫方式

// 在既有 main() 的執行邏輯處，依 phase 分流
async function main() {
    const config = await loadConfig();           // 沿用 01.1 既有的設定載入邏輯
    const mcpClient = await connectMcpServer();   // 沿用 01.1 既有的 MCP 連線邏輯

    if (phase === "init") {
        await runInitPhase(mcpClient, config);    // 對應 01.1 既有邏輯，原封不動搬進這個函式
    } else if (phase === "planning") {
        await runPlanningPhase(mcpClient, config); // 本節「動手事項二」新增的函式
    }
}
```

> 若你目前的 `mcp_orchestrator.mjs` 不是用 `main()` 這種單一進入點寫法，請依實際結構找到「程式真正開始執行」的那一行，邏輯一樣是「讀 `phase` 參數 → 分流呼叫對應函式」，寫法可以照你原本的風格調整，重點是**分流判斷要新增，不能只是憑空多一個 CLI flag 卻沒人讀它**。

### ✋ 動手事項二：新增 `runPlanningPhase()` 函式

**現在要做什麼**：在 `mcp_orchestrator.mjs` 檔案中，找一個跟 01.1 既有的初始化邏輯函式（你在動手事項一改出來的 `runInitPhase`）**同層級**的地方，整個貼上下面這個新函式（不是另開新檔案，是同一份 `.mjs` 裡多一個 function，貼在哪一行不重要，只要跟其他 function 同一層、且在動手事項一的 `main()` 呼叫得到它的位置之前即可）。

**怎麼操作**：下面是完整版 `runPlanningPhase()`，內部依序做三件事（對應原本拆開講解的「自動步驟 1～3」，這裡直接整合成一段，**整塊複製貼上**即可，不用自己手動拼接）：

```javascript
async function runPlanningPhase(mcpClient, geminiClient, config) {
    const { issueIid, techStack, codeRepoPath } = config;

    // ── 自動步驟 1：判斷這次留言事件該不該處理 ──────────────────
    const notes = await mcpClient.callTool({ name: "get_notes", arguments: { issueIid } });
    const latestNote = notes[notes.length - 1];

    if (latestNote.author.username === config.botUsername) {
        console.log("[skip] 最新留言是機器人自己貼的，略過");
        return;
    }

    const hasSpecDraft = notes.some(n => n.body.includes(`[${techStack}] Spec Draft`));
    if (!hasSpecDraft) {
        console.log("[skip] Phase 1 尚未產出 Spec Draft，略過");
        return;
    }

    const alreadyBranched = notes.some(n => n.body.includes(`[${techStack}] 已建立分支`));
    if (alreadyBranched) {
        console.log("[skip] 已建立過分支，略過");
        return;
    }

    const isApproval = latestNote.body.trim() === "Approved";

    // ── 自動步驟 2：草稿迭代（留言不是 Approved 時走這支） ──────────
    if (!isApproval) {
        const specDraft = extractLatestSpecDraftFromNotes(notes, techStack); // 取 Phase 1 留言內容
        const projectYml = await mcpClient.callTool({
            name: "get_file_content",
            arguments: { projectPath: codeRepoPath, filePath: ".agentic/project.yml" }
        });

        const planDraft = await generateContentWithRetry(geminiClient, {
            model: config.geminiModel,
            systemPrompt: PLANNING_SYSTEM_PROMPT,   // 內含本文件附錄 B 範本，需自行定義此常數
            contents: buildPlanningPrompt({ specDraft, latestHumanNote: latestNote.body, projectYml }),
            tools: ["create_note"],                 // 草稿階段只開放唯讀＋留言，不開放寫入
        });

        await mcpClient.callTool({
            name: "create_note",
            arguments: { issueIid, body: `# PLAN.md Draft - Issue #${issueIid} [${techStack}]\n\n${planDraft}` }
        });
        return; // 草稿迭代到此結束，等待人類下一輪留言
    }

    // ── 自動步驟 3：核准動作（留言精確為 Approved 時走這支） ────────
    const finalPlan = extractLatestPlanFromNotes(notes, techStack); // 取最新一版 PLAN.md 草稿內容
    const branchName = `feature/issue-${issueIid}`;

    await mcpClient.callTool({
        name: "create_branch",
        arguments: { projectPath: codeRepoPath, branch: branchName, ref: "main" }
    });

    await mcpClient.callTool({
        name: "create_or_update_file",
        arguments: {
            projectPath: codeRepoPath,
            branch: branchName,
            filePath: ".agentic/PLAN.md",
            content: finalPlan,
            commitMessage: `chore(#${issueIid}): commit approved PLAN.md`
        }
    });

    await mcpClient.callTool({
        name: "create_note",
        arguments: {
            issueIid,
            body: `[${techStack}] 已建立分支 \`${branchName}\`，PLAN.md 已 commit 至分支根目錄，Phase 3 即將開始。`
        }
    });

    await updateIssueLabel(issueIid, {
        remove: "status::waiting-human-plan-approval",
        add: "status::executing"
    });
}
```

**會產生什麼結果**：函式貼上、`main()` 裡的分流（動手事項一）接上之後，第 1～2 節描述的日常操作流程才會真的對應到實際程式行為。

**改完還要做兩件事，照下面指令操作：**

**1. 在 `ai-engine` 倉庫打新 tag**

```bash
# 在 ai-engine 倉庫的本地資料夾內執行
git add mcp_orchestrator.mjs
git commit -m "feat: 新增 Phase 2 planning 邏輯（runPlanningPhase）"
git push origin main

git tag v1.1.0
git push origin v1.1.0
```

**結果**：GitLab 上的 `ai-engine` 倉庫會多一個 `v1.1.0` 標籤，指向你剛剛改完的這版 `mcp_orchestrator.mjs`。可以到倉庫頁面左側 **Repository → Tags** 確認有沒有出現 `v1.1.0`。

**2. 把兩個業務倉庫的 `.gitlab-ci.yml` 裡的版號文字改掉**

打開 `gov-tender-fetcher-frontend` 與 `gov-tender-fetcher-backend` 各自的 `.gitlab-ci.yml`，找到這一行（兩個倉庫的 `ai_pipeline_init` job 裡應該都有，可能目前寫的是 `v1.0.0`）：

```bash
ENGINE_VERSION="v1.0.0"
```

改成：

```bash
ENGINE_VERSION="v1.1.0"
```

兩個倉庫都要改（前端一次、後端一次），改完直接 commit、push 到各自的 `main`：

```bash
git add .gitlab-ci.yml
git commit -m "chore: 升級 ai-engine 至 v1.1.0，支援 Phase 2 planning"
git push origin main
```

**結果**：之後 CI 跑 `ai_pipeline_init`（Phase 1）跟 `ai_pipeline_plan`（Phase 2，第 4 節會教怎麼加）都會下載到 `v1.1.0` 版的 `mcp_orchestrator.mjs`，兩個 stage 用的是同一份、同一個版本的引擎檔案。

> 這就是 01.1 強調的版本 Pinning 機制：業務倉庫永遠用明確的版號字串去抓 `ai-engine` 的內容，不會因為 `ai-engine` 之後又有新 commit 就被影響，要升級永遠是你手動改這一行版號才會生效。

> ⚠️ **三個未定義的輔助函式**：上面用到的 `extractLatestSpecDraftFromNotes()`、`extractLatestPlanFromNotes()`、`updateIssueLabel()`，是這份新函式邏輯上需要、但你目前的 `mcp_orchestrator.mjs` 可能還沒有的小工具函式（純字串解析與 GitLab Label API 呼叫，不涉及 MCP）。這三個要嘛你已經在 01.1 裡有類似的（直接重用），要嘛需要另外補上，**不算複雜，但別漏掉**，否則 `runPlanningPhase()` 會直接噴 `ReferenceError`。

> ⚠️ **工具套件對應提醒**：`create_branch`、`create_or_update_file` 為功能性命名，實際呼叫時請依 01.1 第 6 節所用 `@ttpears/gitlab-mcp-server` 套件當前版本的真實工具名稱與參數 schema 調整（套件更新可能變動命名），上線前務必先以單一測試 Issue 跑過一次完整核准流程再正式啟用。

## ⚙️ 4. `.gitlab-ci.yml` 新增 Stage

**現在要做什麼**：在 `ai-engine` 完成第 3 節的程式碼修改並升版 tag 之後，回到**兩個業務倉庫**，各自編輯自己的 `.gitlab-ci.yml`，新增 `plan` stage。

**沒錯，是同一段結構貼兩次**，前後端各貼一次到各自倉庫的 `.gitlab-ci.yml`，**兩份內容唯一的差異是 `--tech-stack` 參數**（前端填 `react`、後端填 `python`），其他全部一樣（`ENGINE_VERSION`、`stage` 名稱、`variables` 都相同）。下面直接給兩份完整版本，照各自倉庫對應的那份整段貼上即可，不用自己改參數。

**怎麼操作**：在既有 `stages` 陣列補上 `plan`，貼上對應的 `ai_pipeline_plan` job 定義，commit 並 push 到 `main`：

**會產生什麼結果**：之後每次留言事件，CI 會多跑一個 `plan` stage，由內部邏輯判斷要不要真的動作。**這一步做完，第 2 節描述的日常操作流程才會真的生效。**

**補充註記（部署時容易踩到的兩個坑）：**

- **檔案性質跟 `mcp_orchestrator.mjs` 不一樣**：`mcp_orchestrator.mjs`／`mcp_config.json` 是 CI 執行期才用 curl 動態下載、不進版控；`.gitlab-ci.yml` 則是業務倉庫本身要 commit、push 的實體檔案，跟你平常改程式碼流程一樣。
- **版號要對齊**：上面 `ENGINE_VERSION="v1.1.0"` 必須跟第 3 節「動手事項二」實際升級打的 tag 一致，版號對不上會抓到還沒有 `runPlanningPhase()` 的舊版引擎，Phase 2 一樣不會動作。
- **不要用 GitLab `rules` 去區分「這是 Issue 事件還是 Comment 事件」**：GitLab 原生 Trigger API 不會自動帶出可靠的事件類型變數，硬要在 `rules` 層判斷容易誤判。穩健做法是讓 `init` 與 `plan` 兩個 stage 每次都跑，各自在程式內部用第 3 節 `shouldProcessPlanningEvent()` 自行判斷「現在輪到我做事嗎」，不該做的就直接結束——這跟 01.1 的去重設計是同一套哲學。

## 🧪 5. 部署後的第一次測試（Smoke Test）

> 第 1～4 節做完，才會有東西可以測試。本節走一次完整流程，確認真的有接上，**這是接下來能不能正常使用的關鍵驗證步驟**。

**現在要做什麼**：找一個已經跑完 Phase 1（Issue 上已經有 `[react]`／`[python]` Spec Draft 留言）的測試用 Issue，手動觸發一次 Phase 2 流程。

**怎麼操作**，依序執行：

1. **測試「草稿迭代」分支**：在這個 Issue 下方留言，內容隨便寫一句修正意見，例如「請補充一下分頁的預設筆數」。
2. 等待 30 秒～1 分鐘，**到 GitLab 左側 CI/CD → Pipelines**，確認剛剛有新的一次 Pipeline 跑起來，且看到 `plan` stage（不是只有 `init`）。
3. 點進該次 Pipeline 的 `ai_pipeline_plan` job，看 Log 有沒有報錯（常見錯誤是第 3 節提到的三個輔助函式沒定義、或工具名稱跟套件版本對不上）。
4. 回到 Issue，確認多了一則「PLAN.md Draft」留言，內容看起來合理。
5. **測試「核准」分支**：在 Issue 回覆精確字串 `Approved`。
6. 等待同樣時間，再次確認 Pipeline 跑了 `plan` stage 且成功。
7. 確認三件事都發生了：
    - 倉庫多了一個分支 `feature/issue-{IID}`（左側 Repository → Branches 看得到）
    - 該分支根目錄有 `.agentic/PLAN.md` 檔案，內容是核准前最後一版草稿
    - Issue 標籤從 `status::waiting-human-plan-approval` 變成 `status::executing`
8. **前後端都各測一次**（因為兩個倉庫的 `.gitlab-ci.yml` 是分開部署的，一個測過不代表另一個有接上）。

**會產生什麼結果**：八步都過，代表 Phase 2 整條鏈路（Webhook → CI → MCP → Gemini → GitLab 寫入）正常運作，之後就照第 2 節的日常流程使用即可。任何一步卡住，回到附錄 D「除錯資源」對應排查。

> 以下幾節**不是操作步驟**，是給你、Gemini、Claude Code 在日後查閱用的規範文件——定義格式、定義誰能讀寫什麼、定義出錯時去哪裡查。第一次部署不需要照著「做」，但建議讀過一遍知道有這些東西存在，之後 Phase 3／4／5 的文件會回頭引用這裡的定義。

### 📐 A. 與下游階段的引用關係

|下游階段|如何引用本階段產出|禁止事項|
|---|---|---|
|Phase 3（TDD 執行）|讀取分支根目錄 `.agentic/PLAN.md`，作為 `skills/feasibility_check.md` 的校驗基準與 TDD 測試案例來源|不得自行定義另一份計畫格式；PLAN.md 在分支內視為唯讀凍結文件（見附錄 C.1）|

### 📄 B. PLAN.md 唯一權威範本

> **讀者不需要手動建立這個檔案**——這是 Gemini 在第 3 節「自動步驟 2／3」自動生成、自動貼上 Issue、最終自動 commit 進分支的產出物。本節的用途是讓你**審查時知道該預期看到什麼格式**，不是給你照著手打的範本。

```markdown
# Agent Execution Plan - Issue #{ISSUE_IID}

## 1. Core Objective
- [ ] <目標一，須可被客觀驗證>
- [ ] <目標二（如有）>

## 2. Architectural Boundary & Skills
- Tech Stack: <依 .agentic/project.yml 之 tech_stack 填入>
- Layer Convention: <依 .agentic/project.yml 之 layer_convention 填入>
- Boundary: <明確限定本次任務的修改範圍，須與 .agentic/architecture_rules.md 不牴觸>

## 3. API / Interface Contract（如涉及前後端介接才需要）
- <新增或變更的 API 端點 / 元件 Props / State 介面>

## 4. TDD Test Cases to Add
- [ ] test_<情境一>_<預期結果>()
- [ ] test_<情境二>_<預期結果>()

## 5. Modified / Created Files
- <依分層列出完整檔案路徑>

## 6. Risk & Rollback Notes
- 風險：<本次變更的潛在風險>
- 緩解：<對應緩解或回滾策略>

---
## 下一階段
若此計畫符合預期，請回覆 `Approved`，管線將自動建立分支並流轉至 Phase 3（TDD 執行）。
若需修改，請直接以留言描述修正方向，Gemini 將重新生成本計畫。
```

**範例（僅供格式參考，不代表特定技術棧綁定）：**

```markdown
# Agent Execution Plan - Issue #101

## 1. Core Objective
- [ ] 實作標案列表查詢功能的分頁與條件篩選

## 2. Architectural Boundary & Skills
- Tech Stack: Python 3.11 / FastAPI / Pydantic v2
- Layer Convention: Router → Service → Repository
- Boundary: 僅允許修改 app/api/v1/endpoints/tenders.py、app/services/tender_service.py、app/repositories/tender_repository.py

## 3. API / Interface Contract
- GET /api/v1/tenders?page=&keyword=&status=

## 4. TDD Test Cases to Add
- [ ] test_get_tenders_returns_paginated_result()
- [ ] test_get_tenders_filters_by_keyword()

## 5. Modified / Created Files
- app/api/v1/endpoints/tenders.py
- app/services/tender_service.py
- app/repositories/tender_repository.py

## 6. Risk & Rollback Notes
- 風險：篩選條件若未加索引可能造成查詢效能下降
- 緩解：於 Repository 層加上對應欄位索引建議，並於 PR 描述中註記
```

### 🚦 C. 管線控制柵欄

### C.1 計畫凍結原則（Plan Freeze）

`.agentic/PLAN.md` 一旦 commit 進分支即視為**凍結文件**。Phase 3 執行期間若 Claude Code（透過 `skills/feasibility_check.md`）或人類發現計畫與現實不符，正確處理方式是中止並回到 Phase 2 重新核准，**不允許任何 Agent 在執行期間私自竄改 PLAN.md**。

### C.2 核准字串嚴格比對

僅接受精確字串 `Approved`（區分大小寫）觸發分支建立與檔案寫入，避免「看起來不錯」「可以」等模糊留言被誤判。

### C.3 寫入型工具僅在核准分支開放

`create_branch`、`create_or_update_file` 兩個寫入工具只在第 3 節「自動步驟 3」傳給 Gemini 的 `tools` 參數中出現，草稿迭代（自動步驟 2）全程只給 `create_note`，維持唯讀，降低誤操作面積。

### C.4 重複觸發防護

延續 01.1 的去重邏輯模式，本階段以「Issue 留言中是否已出現 `[${techStack}] 已建立分支` 標記」作為冪等性判斷依據，防止同一個 `Approved` 留言因 Webhook 重複送達而建立兩次分支。

### C.5 版本歷程即留言串

不另外維護 PLAN.md 的 diff 版本檔案，Issue Comment 串本身即是版本歷程與人類決策的稽核軌跡。

### 📋 D. 除錯資源

沿用 01.1 第 10 節相同的三個除錯入口（GitLab Pipeline Log、Issue 留言、Webhook 投遞紀錄），額外注意：

- 若回覆 `Approved` 後沒有任何反應，先檢查 Webhook 是否已勾選 `Comment events`（第 1 節），這是最常見的漏設項目。
- 若同一個 `Approved` 觸發了兩次分支建立，檢查第 3 節「自動步驟 1」的去重判斷是否正確讀到 `已建立分支` 標記留言。
