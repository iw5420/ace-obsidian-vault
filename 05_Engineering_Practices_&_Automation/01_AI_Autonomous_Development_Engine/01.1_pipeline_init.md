# 01.1 Pipeline Initialization & Context Assembly (MCP Driven) - Specification v3

本文件定義 **Heroic AI 全自動化開發引擎** 的階段一（Phase 1：管線初始化與動態上下文組裝）之實作規範。 本版本（v3）為**實機驗證通過版本**，根據實際部署除錯過程，修正了 v2 文件中與真實可運行程式碼的落差，包含：MCP SDK 套件更換、ESM 模組改寫、雙專案路徑區分、Issue 動態查詢、去重機制等關鍵修正。

> **關於 Gemini 模型選用的設計決策**：Phase 1（盤點）與 Phase 5（MR Review）使用 Gemini 而非 Claude，理由如下：
> 
> 1. **成本控制**：唯讀盤點與靜態 diff 審查屬於批次任務，Gemini Flash/Flash-Lite 的極低成本符合此場景。
> 2. **專家分工原則**：業界主流策略是「為每個任務編排對的模型」，而非單一模型包辦。Claude Code 額度保留給 Phase 4 本地 TDD 執行，這是它最具優勢的場景（多輪工具調用穩定性）。
> 3. **免費額度考量**：實測中 `gemini-2.5-flash` 在免費方案下每日請求數可能僅 20 次，測試階段建議改用 `gemini-3.1-flash-lite`（每日額度可達 500 次），正式上線後再依需求升級為付費方案並換回更強模型。

## 🗺️ 0. 架構總覽與設計決策

### 0.1 為什麼需要三個倉庫（方案 C）

原規格假設的是 monorepo 結構（前後端同一倉庫）。本專案採前後端分離，若 Issue 僅存在其中一個倉庫，會造成以下問題：

|問題|說明|
|---|---|
|需求碎片化|同一個功能需求（如「標案列表」）要分開開兩個 Issue，語意割裂|
|盤點不完整|Gemini 只能看到自己那端的倉庫，無法評估前後端介面契約|
|Token 授權複雜|若讓 backend CI 去讀 frontend Issue（或反之），需要跨倉庫 token 設定|

**解法：引入第三個倉庫 `gov-tender-fetcher` 作為純 Issue Tracker。**

```
需求（Issue）  ≠  實作（Code）
```

這完全符合原始理念：Issue 是需求的宣告，倉庫是實作的容器，兩件事語意分離。

### 0.3 v3 與 v2 的關鍵差異（實機驗證後修正）

|項目|v2（規劃版）|v3（實機驗證版）|修正原因|
|---|---|---|---|
|引擎倉庫名稱|`heroic-ai-engine`|`ai-engine`|統一以實際建立的倉庫名稱為準|
|引擎倉庫可見度|未特別說明|必須處理 Private 倉庫驗證|Private 倉庫的 raw 檔案需帶 `PRIVATE-TOKEN` header 才能下載，否則被導向登入頁|
|MCP SDK 套件|`@modelcontextprotocol/client`（不存在的套件名）|`@modelcontextprotocol/sdk`|前者是尚未發布的 2.0 拆分套件命名，穩定版必須用後者|
|主程式模組系統|CommonJS（`.js` + `require`）|ESM（`.mjs` + `import`）|官方 SDK 為 ESM-only，`require()` 會丟出 `ERR_PACKAGE_PATH_NOT_EXPORTED`|
|GitLab MCP Server|`@modelcontextprotocol/server-gitlab`|`@ttpears/gitlab-mcp-server`|官方套件已停止維護（最後更新 2025.4.25），其 schema 格式與新版 SDK 不相容|
|GitLab Server 環境變數|`GITLAB_PRIVATE_TOKEN`|`GITLAB_TOKEN`|新套件改用 `GITLAB_URL` + `GITLAB_TOKEN`|
|MCP 工具名稱|`gitlab_get_issue`、`filesystem_read_file` 等|`get_issues`、`get_file_content`、`browse_repository`、`get_notes`、`create_note`|換套件後工具命名空間完全不同|
|Issue IID 取得方式|依賴 `$CI_EXTERNAL_ISSUE_IID`（GitLab 內建變數）|程式啟動後主動查詢 GitLab API|Trigger API 觸發時該內建變數不存在，必須改為主動查詢最新符合條件的 Issue|
|專案路徑判斷|單一 `projectId`|明確區分 `issueTrackerPath`（Issue Tracker）與 `codeRepoPath`（程式碼倉庫，取自 `CI_PROJECT_PATH`）|若不區分，Gemini 會在程式碼倉庫裡找 Issue、或在 Issue Tracker 裡找原始碼，導致工具呼叫失敗|
|Gemini 工具 Schema|直接把 MCP tool 物件丟給 Gemini|新增 `toGeminiFunctionDeclaration()` 轉換層|MCP 的 `inputSchema`/`title`/`annotations` 欄位 Gemini API 不認得，需轉換成 `name`/`description`/`parameters`|
|503 過載處理|無|新增 `generateContentWithRetry()` 指數退避重試|Gemini API 偶發 503 UNAVAILABLE，需自動重試而非直接失敗|
|重複觸發防護|無|新增 `hasExistingSpecDraft()` 去重檢查|GitLab 對「先建立 Issue、後加標籤」會分別觸發 `open` 與 `update` 兩個事件，導致同一個 Pipeline 被觸發兩次|
|Spec Draft 標題格式|無區分標記|標題加上 `[${techStack}]` 後綴|前後端共用同一個 Issue Tracker 專案，若標題沒有技術棧區分，去重檢查會誤判跨專案的留言為重複|

## 📂 1. 四倉庫實體檔案拓撲

### A. 中央 AI 引擎倉庫 (`ai-engine`)

所有業務專案都會在執行期透過 CI 動態引用此處的設定與客戶端。**此倉庫必須為 Private 或 Internal，CI 下載時須帶上 `PRIVATE-TOKEN` header 驗證。**

ai-engine/

## 🛠️ 2. 前置作業：你需要手動完成的事（一次性）

以下步驟**只需要做一次**。完成後，未來每次開新 Issue 只需打標籤即可。

### 步驟 A：建立 `ai-engine` 中央倉庫

1. 在 `http://10.0.0.10/ai-test/` 下建立新的空白倉庫，命名為 `ai-engine`。
    
2. 將第 6 節的 `mcp_config.json` 與 `mcp_orchestrator.mjs` 放入倉庫根目錄。
    
3. 若該專案有走 dev/main 分支策略，先在 `dev` 提交，merge 到 `main` 後再打 tag：
    

```bash
git clone http://10.0.0.10/ai-test/ai-engine.git
cd ai-engine
git checkout -b dev

# 放入 mcp_orchestrator.mjs、mcp_config.json

git add .
git commit -m "init: add mcp_orchestrator and mcp_config"
git push origin dev

git checkout main
git merge dev
git push origin main

git tag v1.0.0
git push origin v1.0.0
```

> ⚠️ **版本 Pinning 原則**：業務專案的 CI 會指定抓取特定 tag 版本（如 `v1.0.0`），而非 `main` 分支。這確保中央倉庫的任何更新不會靜默破壞業務 CI，升級是**明確的人類決策**。
> 
> ⚠️ **若日後修改了 `ai-engine` 的程式碼但 tag 已存在**：tag 是固定指向某個 commit，不會自動跟著 main 移動。必須重新打 tag 才能讓業務 CI 抓到新版內容：
> 
> ```bash
> git tag -d v1.0.0
> git push origin :refs/tags/v1.0.0
> git tag v1.0.0
> git push origin v1.0.0
> ```

### 步驟 B：建立 `gov-tender-fetcher` Issue Tracker 倉庫

1. 在 `http://10.0.0.10/ai-test/` 下建立新的空白倉庫，命名為 `gov-tender-fetcher`。
2. 確認 **Issues 功能已啟用**（Settings → General → Visibility → Issues: ✅）。
3. 進入**左側選單 → Manage → Labels**，新增標籤 `agent::enable`（任意顏色）。
4. 記下此倉庫的**數字 Project ID**（Settings → General 頁面頂部），後續步驟會用到。

### 步驟 C：在前端業務專案設定 GitLab CI/CD 變數

前往 `gov-tender-fetcher-frontend` 倉庫的 **Settings → CI/CD → Variables**，新增以下變數（均設為 `Masked`）：

|變數名稱|說明|取得方式|
|---|---|---|
|`PROJECT_ACCESS_TOKEN`|本倉庫的存取 Token，需有 `api` scope（此 Token 也用於下載 `ai-engine` 的私有檔案，故需有跨專案讀取權限）|Settings → Access Tokens|
|`ISSUE_TRACKER_PROJECT_ID`|`gov-tender-fetcher` 倉庫的數字 ID|步驟 B 記下的值|
|`GEMINI_API_KEY`|Google Gemini API 金鑰|Google AI Studio|

> `CI_API_V4_URL` 與 `CI_PROJECT_PATH` 是 GitLab 內建變數，**不需要手動設定**。

### 步驟 D：在後端業務專案設定 GitLab CI/CD 變數

前往 `gov-tender-fetcher-backend` 倉庫的 **Settings → CI/CD → Variables**，新增相同的三個變數（`PROJECT_ACCESS_TOKEN` 要用**後端倉庫自己的** Access Token, 均設為 `Masked`）：

|變數名稱|說明|
|---|---|
|`PROJECT_ACCESS_TOKEN`|後端倉庫的存取 Token（api scope）|
|`ISSUE_TRACKER_PROJECT_ID`|與前端填相同的值（同一個 Issue Tracker）|
|`GEMINI_API_KEY`|與前端填相同的值|

### 步驟 E：在兩個業務專案佈署韁繩文件

將第 5 節的所有檔案分別放入兩個業務專案倉庫，**依技術棧填入對應內容**。

### 步驟 F：安裝並註冊 GitLab Runner（若尚未設置）

確認業務專案的 **Settings → CI/CD → Runners** 有 Active 的 Runner。若沒有：

```bash
# 安裝 GitLab Runner（以 CentOS Stream 為例）
curl -L https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.rpm.sh -o script.rpm.sh
sudo bash script.rpm.sh
sudo dnf install -y gitlab-runner

# 安裝 Docker（executor 需要）
sudo dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io
sudo systemctl enable --now docker

# 註冊 Runner（Group 層級，前後端共用同一個 Runner）
sudo gitlab-runner register \
  --url http://10.0.0.10 \
  --token <在 GitLab Group → Settings → CI/CD → Runners 取得>
```

互動式問答時：

- Executor 選 `docker`
- Default Docker image 填 `node:20-slim`

> ⚠️ Executor 一定要選 `docker`，因為 `.gitlab-ci.yml` 用 `image: node:20-slim` 指定容器，若選 `shell` executor 會直接在機台上跑、找不到指定 image 而失敗。

### 步驟 G：設定 Webhook 觸發兩條 Pipeline

**順序：**

```
步驟 G：設定 Webhook（前置作業，只做一次）
        ↓
日常使用：開 Issue + 打 agent::enable 標籤
        ↓
Webhook 自動觸發 Pipeline
```

由於 Issue 開在 `gov-tender-fetcher`，需要用 Webhook 通知兩個業務專案的 CI。**Webhook 必須使用 GitLab 標準 Trigger API 格式，不能用網頁瀏覽路徑**：

```
正確：http://10.0.0.10/api/v4/projects/{數字PROJECT_ID}/trigger/pipeline?token={TRIGGER_TOKEN}&ref=main
錯誤：http://10.0.0.10/ai-test/{專案路徑名稱}/refs/heads/main/trigger/pipeline?token=xxx
```

> 網頁瀏覽路徑（如 `/ai-test/gov-tender-fetcher-frontend`）是給人看的，GitLab 會把它對應到背後的數字 Project ID，但 Webhook 呼叫的是 REST API，API 路徑規則固定是 `/api/v4/projects/{數字ID}/...`，必須用數字 ID 不能用路徑名稱。

**取得數字 Project ID**：前往各業務專案的 Settings → General，頁面最上方會顯示 `Project ID`。

**取得 CI Trigger Token**：前往各業務專案的 Settings → CI/CD → Pipeline triggers，新增一個 trigger token。

**前往 `gov-tender-fetcher` 倉庫的 Settings → Webhooks，新增兩條 Webhook：**

**Webhook 1（觸發前端）：**

```
http://10.0.0.10/api/v4/projects/{前端數字PROJECT_ID}/trigger/pipeline?token={前端TRIGGER_TOKEN}&ref=main
```

- 觸發事件：勾選 `Issue events`
- Enable SSL verification **不要勾**（內部 GitLab 為 HTTP，非 HTTPS）

**Webhook 2（觸發後端）：**

```
http://10.0.0.10/api/v4/projects/{後端數字PROJECT_ID}/trigger/pipeline?token={後端TRIGGER_TOKEN}&ref=main
```

- 觸發事件：勾選 `Issue events`
- Enable SSL verification **不要勾**

> ⚠️ **重複觸發是已知限制，非設定錯誤**：GitLab 對於「先建立 Issue（無標籤）、之後再加上 `agent::enable` 標籤」這個操作序列，會分別送出 `action: "open"` 與 `action: "update"` 兩個獨立的 webhook 事件，導致每個業務專案的 Pipeline 各被觸發兩次。GitLab webhook 原生**沒有**依標籤值過濾事件的機制（這是平台限制，業界對此的標準解法是在程式內做冪等性 / 去重處理，詳見第 6 節 `hasExistingSpecDraft()`）。

> ⚠️ 本步驟為一次性基礎建設，必須在開第一個 Issue 之前完成。完成後，未來每次在 Issue 打上 `agent::enable` 標籤即會自動觸發，無需再動 Webhook 設定。

## 🔄 3. 每次使用流程（日常操作）

完成前置作業後，**每次開新需求的操作只有兩步**：

```
1. 在 gov-tender-fetcher 開 Issue，描述完整的全功能需求

2. 在 Issue 上打上 agent::enable 標籤
         ↓

         ↓
3. Webhook 觸發前端 + 後端兩條 Pipeline
         ↓
4. 兩個 CI 容器啟動，各自 curl 下載引擎、讀取自己的韁繩文件
         ↓
5. 各自 Pipeline 先做去重檢查：若這個 Issue 已經有自己技術棧的 Spec Draft 留言，直接跳過結束
         ↓
6. 未跳過者：Gemini 主動查詢符合條件的 Issue，盤點對應的程式碼倉庫，生成 Spec Draft
         ↓
7. 兩則 Spec Draft（標題分別帶 [react] / [python]）分別貼回同一個 Issue 留言
         ↓
8. 你去 Issue 留言查看兩份報告，確認前後端規格對齊後回覆 Approved
```

> 等待時間約 **1～3 分鐘**。由於 GitLab webhook 對單一標籤操作可能觸發兩次事件，同一個專案可能會看到兩條 Pipeline 紀錄，但去重機制會確保只有一份留言被實際產出。

## 🔄 4. 容器內自動執行細節

> 本節說明 CI 容器內部自動發生的事，**讀者不需要手動執行任何指令**，此處僅供理解與除錯參考。

### 自動步驟 1：建立執行沙盒並動態下載中央配置

GitLab Runner 啟動 `node:20-slim` 容器，自動將業務專案的程式碼 clone 到 `/builds/...`。隨後安裝 npm 依賴、透過 `curl` 下載中央引擎（版本固定，帶上 Private Token 驗證）：

```bash
apt-get update && apt-get install -y curl git
npm install @modelcontextprotocol/sdk @google/genai

mkdir -p .agentic/runtime
ENGINE_VERSION="v1.0.0"
BASE_URL="http://10.0.0.10/ai-test/ai-engine/-/raw/${ENGINE_VERSION}"

curl -sf --header "PRIVATE-TOKEN: ${PROJECT_ACCESS_TOKEN}" \
  "${BASE_URL}/mcp_orchestrator.mjs" -o .agentic/runtime/mcp_orchestrator.mjs \
  || { echo "[-] 致命錯誤：無法下載引擎腳本"; exit 1; }

curl -sf --header "PRIVATE-TOKEN: ${PROJECT_ACCESS_TOKEN}" \
  "${BASE_URL}/mcp_config.json" -o .agentic/runtime/mcp_config.json \
  || { echo "[-] 致命錯誤：無法下載 MCP 配置"; exit 1; }
```

> ⚠️ **為何需要 `PRIVATE-TOKEN` header**：`ai-engine` 是 Private 倉庫，未帶驗證的 `curl` 請求會被 GitLab 導向登入頁（HTTP 302），下載到的會是空內容而非實際檔案，且 `curl -f` 不會偵測到這個失敗（302 不算 HTTP error）。

### 自動步驟 2：主動查詢目標 Issue 與去重檢查

調度程式啟動後，**不依賴 GitLab Webhook 帶入的 Issue IID**（因為透過 Trigger API 觸發時，GitLab 不會自動帶入 `CI_EXTERNAL_ISSUE_IID`），而是主動向 GitLab API 查詢：

```
GET /projects/{ISSUE_TRACKER_PROJECT_ID}/issues
    ?labels=agent::enable&state=opened&order_by=updated_at&sort=desc&per_page=1
```

取得最新一筆符合條件的 Issue 後，立即進行去重檢查：查詢該 Issue 底下的留言，若已存在標題包含 `[${techStack}]` 標記的 Spec Draft，判定為重複觸發，直接結束（exit 0），**不會啟動 MCP 連線、不會呼叫 Gemini API**。

### 自動步驟 3：記憶體注入憑證並啟動 GitLab MCP Server

調度程式在**記憶體中**組裝含 GitLab Token 的環境變數，**不寫回磁碟**，防止憑證洩漏：

```
node mcp_orchestrator.mjs
 └── npx @ttpears/gitlab-mcp-server   ← 子行程，提供 get_issues / browse_repository / get_file_content / create_note 等工具
```

MCP Server 透過 **stdio** 與主程式通訊，不開任何 port，不走網路。

### 自動步驟 4：區分兩個專案路徑

程式會明確區分兩個不同的 GitLab 專案路徑，並在 system prompt 中告知 Gemini：

|角色|路徑來源|用途|
|---|---|---|
|Issue Tracker 路徑|呼叫 GitLab API 查詢 `path_with_namespace`|僅用於 `get_issues`、`get_notes`、`create_note`|
|程式碼倉庫路徑|GitLab CI 內建變數 `CI_PROJECT_PATH`|僅用於 `browse_repository`、`get_file_content`|

> 若不做此區分，Gemini 可能會在 Issue Tracker（空倉庫）裡找 `.agentic/instructions.md` 而找不到檔案，或反過來在程式碼倉庫裡找 Issue 而找不到。

### 自動步驟 5：Agentic Loop 工具調用鏈

Gemini 自主決定工具調用順序與節奏（單輪可能呼叫一個或多個工具，視模型當下的規劃而定），典型流程：

1. `get_issues(projectPath=Issue Tracker 路徑)` → 讀取需求
2. `get_notes(projectPath=Issue Tracker 路徑)` → 確認既有留言（可選）
3. `browse_repository(projectPath=程式碼倉庫路徑)` → 盤點專案結構
4. `get_file_content(projectPath=程式碼倉庫路徑, filePath=".agentic/instructions.md")` → 讀取技術棧規範
5. `get_file_content(...filePath=".agentic/architecture_rules.md")` → 讀取架構柵欄
6. `get_file_content(...filePath="CLAUDE.md")` → 讀取 Git 工作流規範
7. `create_note(projectPath=Issue Tracker 路徑, body=Spec Draft)` → 貼回 Issue

// 將 MCP tool schema（含 title/inputSchema/annotations）轉換成
// Gemini API 要求的 functionDeclarations 格式（name/description/parameters）
function toGeminiFunctionDeclaration(mcpTool) {
    const { name, description, inputSchema } = mcpTool;
    return {
        name,
        description: description || mcpTool.title || name,
        parameters: stripUnsupportedSchemaFields(inputSchema) || { type: "object", properties: {} }
    };
}

// Gemini 的 parameters schema 不接受 JSON Schema 的部分欄位（如 additionalProperties、$schema）
// 遞迴清除，避免再次出現 "Unknown name" 錯誤
function stripUnsupportedSchemaFields(schema) {
    if (!schema || typeof schema !== "object") return schema;
    const UNSUPPORTED_KEYS = new Set(["additionalProperties", "$schema", "title", "default"]);
    const cleaned = {};
    for (const [key, value] of Object.entries(schema)) {
        if (UNSUPPORTED_KEYS.has(key)) continue;
        if (key === "properties" && typeof value === "object") {
            cleaned.properties = Object.fromEntries(
                Object.entries(value).map(([k, v]) => [k, stripUnsupportedSchemaFields(v)])
            );
        } else if (key === "items") {
            cleaned.items = stripUnsupportedSchemaFields(value);
        } else {
            cleaned[key] = value;
        }
    }
    return cleaned;
}

async function executeTool(mcpClient, toolName, toolArgs) {
    console.log(`  [Tool] 執行: ${toolName}`, JSON.stringify(toolArgs));
    try {
        const result = await mcpClient.callTool({ name: toolName, arguments: toolArgs });
        return { success: true, content: result.content };
    } catch (err) {
        const isEnvError = err.message?.includes("ECONNREFUSED") ||
                           err.message?.includes("not found") ||
                           err.message?.includes("timeout");
        if (isEnvError) {
            console.error(`  [Tool] 環境類錯誤（不重試）: ${err.message}`);
            return { success: false, fatal: true, error: err.message };
        } else {
            console.error(`  [Tool] 邏輯類錯誤: ${err.message}`);
            return { success: false, fatal: false, error: err.message };
        }
    }
}

class EnvFatalError extends Error {
    constructor(message) {
        super(message);
        this.name = "EnvFatalError";
        this.exitCode = 2;

}

const MAX_TOOL_RESULT_CHARS = 8000;
function truncateContent(content) {
    if (!Array.isArray(content)) return content;
    return content.map(item => {
        if (item.type === "text" && typeof item.text === "string" && item.text.length > MAX_TOOL_RESULT_CHARS) {
            return {
                ...item,
                text: item.text.slice(0, MAX_TOOL_RESULT_CHARS) + `\n\n[... 內容過長，已截斷至 ${MAX_TOOL_RESULT_CHARS} 字元 ...]`
            };
        }
        return item;
    });
}

// 針對 Gemini API 暫時性過載（503 UNAVAILABLE）做重試，指數退避
async function generateContentWithRetry(aiClient, requestConfig) {
    const MAX_RETRIES = 4;
    const BASE_DELAY_MS = 3000;

    for (let attempt = 1; attempt <= MAX_RETRIES; attempt++) {
        try {
            return await aiClient.models.generateContent(requestConfig);
        } catch (err) {
            const isOverloaded = err.status === 503 ||
                                 err.message?.includes("UNAVAILABLE") ||
                                 err.message?.includes("high demand");

            if (!isOverloaded || attempt === MAX_RETRIES) {
                throw err;
            }

            const delayMs = BASE_DELAY_MS * Math.pow(2, attempt - 1);
            console.warn(`  [Gemini] 服務暫時過載（503），第 ${attempt}/${MAX_RETRIES} 次重試，等待 ${delayMs / 1000}s...`);
            await new Promise(resolve => setTimeout(resolve, delayMs));
        }
    }
}

async function runAgenticLoop(aiClient, mcpClient, tools, systemInstruction, initialPrompt) {
    const MAX_TURNS = 20;
    let turn = 0;
    const conversationHistory = [
        { role: "user", parts: [{ text: initialPrompt }] }
    ];
    console.log("[*] 啟動 Agentic Loop...");

    while (turn < MAX_TURNS) {
        turn++;
        console.log(`\n[Loop] 第 ${turn} 輪`);

        const response = await generateContentWithRetry(aiClient, {
            model: "gemini-3.1-flash-lite",
            contents: conversationHistory,
            config: {
                systemInstruction,
                tools: [{ functionDeclarations: tools }]
            }
        });

        const candidate = response.candidates?.[0];
        if (!candidate) { console.error("[-] Gemini 未返回有效候選，中止 Loop"); break; }

        const parts = candidate.content?.parts || [];
        const functionCalls = parts.filter(p => p.functionCall);
        const textParts     = parts.filter(p => p.text);

        if (textParts.length > 0) {
            const text = textParts.map(p => p.text).join("");
            console.log(`[Gemini] ${text.slice(0, 200)}${text.length > 200 ? "..." : ""}`);
        }

        if (functionCalls.length === 0) {
            console.log("[+] Gemini 宣告完成（無更多工具調用），退出 Loop");
            break;
        }

        conversationHistory.push({ role: "model", parts });

        const toolResults = [];
        for (const part of functionCalls) {
            const { name, args: fnArgs } = part.functionCall;
            const result = await executeTool(mcpClient, name, fnArgs);
            if (result.fatal) {
                throw new EnvFatalError(`環境類致命錯誤，中止 Loop: ${result.error}`);
            }
            toolResults.push({
                functionResponse: {
                    name,
                    response: result.success
                        ? { content: truncateContent(result.content) }
                        : { error: result.error }
                }
            });
        }

        conversationHistory.push({ role: "user", parts: toolResults });
    }

    if (turn >= MAX_TURNS) {
        console.error(`[-] 警告：已達最大輪次上限 (${MAX_TURNS})，強制退出`);
    }
}

### 8.2 錯誤分類與退出碼

錯誤分兩類處理，避免網路抖動或 Token 失效導致 Gemini 無限重試：

```javascript
// mcp_orchestrator.mjs — executeTool 函式內
async function executeTool(mcpClient, toolName, toolArgs) {
    try {
        const result = await mcpClient.callTool({ name: toolName, arguments: toolArgs });
        return { success: true, content: result.content };
    } catch (err) {
        const isEnvError = err.message?.includes("ECONNREFUSED") ||
                           err.message?.includes("not found") ||
                           err.message?.includes("timeout");
        if (isEnvError) {
            // 環境類錯誤：MCP Server 連不到、Token 失效
            // → 立即標記 fatal，主程式接到後 exit 2，不讓 Gemini 重試
            return { success: false, fatal: true, error: err.message };
        } else {
            // 邏輯類錯誤：工具參數錯誤、Issue 不存在
            // → 回傳錯誤訊息給 Gemini，讓它修正參數後重試
            return { success: false, fatal: false, error: err.message };
        }
    }
}
```

退出碼對照：

|情況|行為|CI Exit Code|
|---|---|---|
|環境類錯誤（MCP 連不到、Token 失效）|立即中止，不重試|`exit 2`|
|邏輯類錯誤（工具參數錯誤）|回傳給 Gemini 讓其重試|繼續 Loop|
|Loop 超過 MAX_TURNS（20 輪）|警告並強制退出|`exit 1`|
|去重檢查命中（重複觸發）|提前結束，不執行任何工具呼叫|`exit 0`|
|任務正常完成|關閉 MCP 連線|`exit 0`|

### 8.3 Gemini API 503 過載重試

Gemini API 偶發回傳 `503 UNAVAILABLE`（服務暫時過載），採指數退避自動重試，避免單次過載直接導致整條 Pipeline 失敗：

```javascript
async function generateContentWithRetry(aiClient, requestConfig) {
    const MAX_RETRIES = 4;
    const BASE_DELAY_MS = 3000;

    for (let attempt = 1; attempt <= MAX_RETRIES; attempt++) {
        try {
            return await aiClient.models.generateContent(requestConfig);
        } catch (err) {
            const isOverloaded = err.status === 503 ||
                                 err.message?.includes("UNAVAILABLE") ||
                                 err.message?.includes("high demand");
            if (!isOverloaded || attempt === MAX_RETRIES) throw err;

            const delayMs = BASE_DELAY_MS * Math.pow(2, attempt - 1);
            console.warn(`服務暫時過載，第 ${attempt}/${MAX_RETRIES} 次重試，等待 ${delayMs / 1000}s...`);
            await new Promise(resolve => setTimeout(resolve, delayMs));
        }
    }
}
```

### 8.4 重複觸發去重機制

GitLab webhook 原生沒有依標籤值過濾事件的能力（這是平台限制，連 GitHub Actions 也有同樣限制），業界標準解法是在程式內做冪等性處理。本架構在**呼叫 Gemini 之前**就先做去重判斷，避免浪費 API 額度：

```javascript
async function hasExistingSpecDraft(config, issueIid, techStack) {
    // 查詢 Issue 留言，比對是否已存在帶有 [techStack] 標記的 Spec Draft
    // 若存在，run() 主流程會直接 return，完全不會啟動 MCP 連線或呼叫 Gemini
}
```

> ⚠️ marker 字串必須包含 `[${techStack}]`，因為前後端共用同一個 Issue Tracker 專案（`CI_PROJECT_ID` 兩邊都指向 `gov-tender-fetcher`），若不區分技術棧，會發生「後端先貼完留言、前端的去重檢查誤判為自己已執行過」的跨專案誤判。

### 8.5 CI Trigger Token 安全說明

Webhook URL 中的 CI Trigger Token 僅用於**觸發 pipeline**，不具備 GitLab API 讀寫 scope，即便外洩也無法操作任何倉庫內容。真正的讀寫憑證（`PROJECT_ACCESS_TOKEN`）只存在於 CI/CD Variables，設為 Masked 後不會出現在任何 pipeline log 中。
