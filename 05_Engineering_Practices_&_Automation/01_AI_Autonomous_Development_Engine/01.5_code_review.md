當 Docker 內所有測試均通過，Claude 自動發起 Git Push，並調用 API 建立 GitLab **Merge Request (MR)**。

```
GitLab MR Created 
  │
  ├──► 1. 觸發 GitLab CI Pipeline ──► 執行 SonarQube / 資安掃描 / 整合測試
  │
  ├──► 2. 觸發 Gemini Pro Reviewer ──► 對照分支出口的 PLAN.md 進行 Code Review
  │                                     (檢查是否滿足當初約定的規格)
  ▼
人類 (Ace) 最終核可 ──► 點擊 Approve & Merge
```

- **Harness 規範（Generator-Critic 模式）**：
    
    - **寫程式的 Agent（Claude）不能當審查員**。
        
    - 由 **Gemini Pro** 扮演 Critic，調用 GitLab MR Diff API。Gemini 的 System Prompt 被賦予頂級企業通用 Clean Code 規範。
        
    - Gemini 會去讀取該分支附帶的 `PLAN.md`。如果發現 Claude 偷偷改了當初沒說要改的檔案，或者少寫了當初約定的測試案例，Gemini 會直接在 GitLab MR 的代碼行上**發起線上 Discussions 提出質疑**。
        
    - 若 Gemini 或 GitLab CI 留下不通過的紀錄，MR 標籤變更為 `status::review-failed`，重回 Phase 2 重擬計畫或修正。
