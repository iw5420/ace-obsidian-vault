# 📑 08.3.5 銜接日誌：從非同步評估（Evaluation）到跨平台權重微調（Training）的工程閉環

> 本篇作為模組三（評估引擎）與模組四（微調核心）之間的邏輯橋樑。我們將定義如何將評估階段發現的「能力缺口」轉化為訓練階段的「梯度增量」，並釐清從 I/O 密集型任務回歸到運算密集型（Compute-Bound）任務時的資源重新調度機制。

## 🧭 1. 任務特徵回歸：從外部 API 呼叫到本地算力榨取

在模組三中，我們透過 `Asyncio` 突破了外部 API 的頻寬限制。進入模組四後，戰場重新回到本地硬體（GPU/MPS/CPU）。這是一次從「等待」到「計算」的典範回歸。

### 資源調度對比矩陣

|**維度**|**模組三：Async Evaluation**|**模組四：LoRA Training**|
|---|---|---|
|**瓶頸來源**|**I/O-Bound (網路延遲)**|**Compute-Bound (矩陣乘法算力)**|
|**核心技術**|`asyncio` + `Semaphore` 控流|`PyTorch` 自研手寫訓練迴路|
|**並行目標**|提高 RPM (每分鐘請求數)|極大化有效 Batch Size (透過梯度累積)|
|**硬體感知**|網路 Socket 緩衝區|實體 VRAM / Unified Memory 監控|

## 🔄 2. 數據平面與權重狀態機的演進 (State Machine)

模組三產出的「差異報告」不只是 Markdown，更是模組四訓練時的「冷啟動」依據。

### 資料與權重流轉生命週期

程式碼片段

```
graph LR
    A[eval_cases.jsonl] -->|模組三：發現弱點| B(差異報告 / 指標低分案例)
    B -->|模組四：訓練輸入| C{LoRA 訓練迴路}
    C -->|梯度發射| D[lora_weights.pt]
    D -->|數學恆等合併| E[Final Merged Model]
```

- **狀態：EVAL_DIAGNOSED**：模組三透過黃金標答（Target Response）比對，精確定位出模型在特定領域（如 SQL 防禦或二元搜尋）的 ROUGE/BLEU 提升空間。
    
- **狀態：TRAINED_INCREMENT**：模組四透過手寫 `MockLinearWithLoRA` 產生權重增量 $\Delta W = (B @ A) * \text{scaling}$，僅優化低秩矩陣以守護 Base Model。
    

## 🛡️ 3. 模組四「跨平台自適應」設計防禦焦點 (Pre-flight Checklist)

在啟動模組四代碼前，架構師必須確保以下防禦機制已寫入 `schema.py` 與 `pipeline.py` 中，拒絕盲目的算力浪費：

- **記憶體溢位防線（OOM Defense）：** 不同於模組三的 `Semaphore` 控流，模組四採用「實體小 Batch Size + 梯度累積（Gradient Accumulation）」技術。這能確保在記憶體受限的設備（如 8GB Mac）上，依然能模擬出頂級企業的大規模訓練效果。
    
- **Bootstrap 環境變數鐵律：** 模組三引入了全域組態與 `.env` 聯動。模組四必須嚴格遵守「最頂層加載 `load_dotenv()`」規範，防止 Hydra 在編譯硬體參數（如 `device`）時因抓不到變數而觸發 `InterpolationResolutionError` 崩潰。
    
- **硬體多型抽象（Hardware Polymorphism）：** 系統必須具備執行期感知能力。不論是 Mac 的 `mps`、Nvidia 的 `cuda` 或是純 `cpu` 環境，`RuntimeHardwareProfiler` 都應能自動切換正確的監測 API，杜絕 `AttributeError`。
    
- **數學恆等性驗證（Inference Optimization）：** 微調完畢後，必須執行 `merge_and_unload()` 演算法。這不僅是為了節省空間，更是為了消除推理時的旁路計算延遲，將微調後的智慧永久性「熔斷」進核心矩陣中。
