模組一與模組二在「代碼執行」與「職責範疇」上的重疊度確實非常低，它們分別代表了生產級系統中兩個截然不同的維度：**控制平面（Control Plane）**與**數據平面（Data Plane）**。

## 🧭 兩個模組的本質區別與邊界

我們可以從以下幾個維度來釐清它們的邊界：

|**維度**|**模組一：動態組態與型態安全**|**模組二：多核心 Data Curation 管道**|
|---|---|---|
|**核心職責**|**守門員與環境感知**<br><br>  <br><br>確保系統啟動時參數合法，並自動偵測本地硬體（如 M4 晶片）。|**吞吐量與數據清洗**<br><br>  <br><br>負責海量文本的 Regex 標準化與 MinHash + LSH 高效去重。|
|**運算特徵**|**I/O 與邏輯校驗密集型**<br><br>  <br><br>耗費時間極短（微秒級），著重於結構校驗（Pydantic v2）。|**CPU 運算密集型 (CPU-Bound)**<br><br>  <br><br>涉及海量字串雜湊運算，需榨乾多核心效能。|
|**狀態特性**|**無狀態 (Stateless)**<br><br>  <br><br>載入並校驗完畢後，組態物件即維持唯讀（Read-Only）。|**混合狀態**<br><br>  <br><br>Worker 進程無狀態，但主進程的 LSH 雜湊桶具備**強狀態（Stateful）**。|

## 🔗 它們唯一的交織點：依賴注入

雖然重疊度極少，但在端到端的完整生命週期中，模組一會透過以下方式**服務**模組二（這也是為什麼模組一被列為起手式）：

1. **並行執行緒/進程數的動態配置**
    
    模組一的 `RuntimeHardwareDetector` 會自動偵測當前環境的實體核心數（例如針對 M4 Pro 的 P-Cores 進行鎖定），並將最優執行緒數寫入組態 `validated_config.optimal_threads`。
    
2. **參數傳遞**
    
    當模組二的 `DataCurationPipeline` 啟動時，它所需的 `num_workers`（工作進程數）以及 MinHash 的 `num_perm`（雜湊置換次數），應該直接從模組一校驗通過的組態物件中讀取，而不是硬編碼（Hardcode）在代碼裡。
    

### 🔄 架構流水線的協同關係

在真實的執行鏈路中，它們是**線性串聯**而非交織在一起的：


```
[ 系統啟動進入點 ]
       │
       ▼
[ 模組一：控制平面 ] ──> 讀取 YAML ──> Pydantic 強型態校驗 ──> 偵測 M4 核心
       │
       └─( 參數注入：num_workers=4, num_perm=128 )
       │
       ▼
[ 模組二：數據平面 ] ──> 啟動 Multiprocessing ──> 大規模清洗去重 ──> 產出乾淨語料
```

這種高度解耦的設計，能確保你在優化模組二的去重演算法（例如調整 Band 數量或優化雜湊函數）時，完全不需要擔心會弄壞模組一的組態邏輯；同理，未來即使將 Hydra 更換為其他組態中心（如 Consul 或 AWS AppConfig），數據清洗管道也能源封不動地繼續運作。
