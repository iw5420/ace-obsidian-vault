# 📑 08.3.5 銜接日誌：從非同步評估（Evaluation）到跨平台權重微調（Training）的工程閉環

> 本篇作為模組三（評估引擎）與模組四（微調核心）之間的架構橋樑。我們將定義如何將評估階段發現的「能力缺口」轉化為訓練階段的「梯度增量」，並釐清從 I/O 密集型任務回歸到運算密集型（Compute-Bound）任務時的資源重新調度機制、資料流與程式控制鏈路。

## 🧭 1. 任務特徵回歸：從外部 API 呼叫到本地算力榨取

在模組三中，我們透過 `Asyncio` 突破了外部 API 的頻寬限制（I/O-Bound）。進入模組四後，戰場重新回到本地硬體（GPU/MPS/CPU）。這是一次從「等待」到「計算」的典範回歸。

### 資源調度對比矩陣

|**維度**|**模組三：Async Evaluation**|**模組四：LoRA Training**|
|---|---|---|
|**瓶頸來源**|**I/O-Bound (網路延遲)**|**Compute-Bound (矩陣乘法算力)**|
|**核心技術**|`asyncio` + `Semaphore` 控流|`PyTorch` 自研手寫訓練迴路|
|**並行目標**|提高 RPM (每分鐘請求數)|極大化有效 Batch Size (透過梯度累積)|
|**硬體感知**|網路 Socket 緩衝區|實體 VRAM / Unified Memory 監控|

## 🔄 2. 資料平面與資產狀態機流轉 (Data Flow Contract)

為了確保模組間的絕對解耦，模組三與模組四不共享運行時的內存物件，而是透過標準化的資料落盤合約進行對接。

### 資料流轉生命週期與狀態機

```
[ data/eval/eval_cases.jsonl ]  <-- 模組二/三產出的基準語料 (唯讀輸入)
       │
       ▼ [狀態：EVAL_DIAGNOSED] 
       │  經由模組三計算出 ROUGE/BLEU 指標，篩選出低分（能力缺口）案例
       │
       ▼ (進入模組四：自定義 Dataset 進行 Tokenization)
[ 狀態：TOKENIZED_TENSORS ] 
       │  依據模型的 max_length 進行對齊與 Padding，轉化為 PyTorch Tensors
       │
       ▼ (進入訓練迴路：前向傳播與反向傳播)
[ 狀態：TRAINED_INCREMENT ]
       │  手寫 MockLinearWithLoRA 產生權重增量 ΔW = (B @ A) * scaling
       │
       ▼ 儲存至落地檔案：ryan_lora_checkpoint.pt
[ 狀態：LORA_WEIGHT_CHECKPOINT ]
       │
       ▼ 執行終極熔斷演算法：merge_and_unload()
[ 狀態：MERGED_BASE_MODEL ] <-- 數學恆等合併完成，消除旁路延遲的完全體
```

### 模組四輸入數據規格合約

模組四將直接讀取模組三評估鏈路中具備黃金標答的數據。每行必須為合法的 JSON 結構，以利流式加載（Streaming）：

JSON

```
{"id": "case_001", "prompt": "請解釋什麼是原子性...", "baseline_response": "...", "target_response": "正確的原子性定義應包含事務的不可分割性..."}
```

## 🔀 3. 程式執行控制流 (Program Control Flow)

以下為進入模組四時，從系統啟動、組態校驗、硬體感知、到執行自定義訓練迴路的完整程式控制順序圖。

程式碼片段

```
sequenceDiagram
    autonumber
    actor Architect as 系統進入點 (main.py)
    participant Boot as Bootstrap (load_dotenv)
    participant Hydra as Hydra 組態編譯器
    participant Schema as Pydantic v2 校驗閘門
    participant Profiler as HardwareProfiler (MPS/CUDA)
    participant Loop as CustomTrainingLoopPipeline

    Architect->>Boot: 1. 於最頂層觸發 load_dotenv()
    Note over Boot: 將 .env 載入作業系統記憶體
    Architect->>Hydra: 2. 觸發 @hydra.main 編態組態樹
    Hydra->>Schema: 3. 橫向串接組態參數 (hparams)
    Note over Schema: 進行強型態完全體防禦校驗
    Schema-->>Architect: 校驗通過，注入組態物件
    Architect->>Profiler: 4. 初始化實體運行期觀測器
    Profiler->>Profiler: 5. 執行動態感知 (偵測為 MPS 或 CUDA)
    Architect->>Loop: 6. 啟動自定義訓練管線
    loop 每一個 Epoch / Batch 迭代
        Loop->>Loop: a. 執行前向傳播 (Forward Pass)
        Loop->>Loop: b. 累積梯度 (Gradient Accumulation)
        Loop->>Loop: c. 手寫反向傳播 (Backward Pass)
        Loop->>Profiler: d. 執行算力 Trace 採樣 (prof.step)
    end
    Loop->>Architect: 7. 訓練完工，回傳收斂 Loss 報告與合併矩陣
```

## 🛡️ 4. 模組四「跨平台自適應」架構防禦焦點

在啟動模組四代碼前，架構師必須確保以下防禦機制已寫入 `schema.py` 與 `pipeline.py` 中，拒絕盲目的算力浪費與核心崩潰：

- **記憶體溢位防線（OOM Defense）：**
    
    不同於模組三的 `Semaphore` 控流，模組四採用「實體小 Batch Size + 梯度累積（Gradient Accumulation）」技術。這能確保在記憶體受限的設備（如 8GB Mac）上，依然能模擬出頂級企業的大規模訓練效果。
    
- **Bootstrap 核心防禦鐵律：**
    
    延續模組三的踩坑經驗，全專案所有包含 `@hydra.main` 裝飾器的啟動腳本，**必須將 `load_dotenv()` 提升至檔案的最頂層（必須在 `import hydra` 之前執行）**。防止 Hydra 在編譯硬體參數（如 `device`）時因抓不到變數而觸發 `InterpolationResolutionError` 崩潰。
    
- **硬體多型抽象（Hardware Polymorphism）：**
    
    系統必須具備執行期感知能力。不論是 Mac 的 `mps`、Nvidia 的 `cuda` 或是純 `cpu` 環境，`RuntimeHardwareProfiler` 都應能自動切換正確的監測 API（例如調用 `torch.mps.synchronize()` 或 `torch.cuda.synchronize()`），杜絕 `AttributeError`。
    
- **數學恆等性驗證（Inference Optimization）：**
    
    微調完畢後，必須執行 `merge_and_unload()` 演算法。這不僅是為了節省空間，更是為了消除推理時的旁路計算延遲，將微調後的智慧永久性「熔斷」進核心矩陣中。
