# 📑 08.2.5 銜接日誌：從多核心 Curation 到非同步高併發 Evaluation 的架構典範轉移

> 本篇作為模組二（數據平面清洗）與模組三（評估引擎）之間的架構橋樑，釐清資料流狀態機轉移、並行模型切換（Multiprocessing vs Asyncio），並預先定義模組三的邊界防禦合約。

## 🧭 1. 並行典範轉移：CPU 密集型 vs I/O 密集型

從模組二跨入模組三，系統的運算特徵發生了根本性的轉變。我們必須精確區分兩種不同的並行通訊模型，以防核心資源錯配：

```Plaintext
[模組二：數據清洗] ─>特徵：CPU-Bound ─>方案：Multiprocessing(多進程) ─>榨乾 M4 P-Cores
                                                                       │
                                                ( 產出：Cleaned Jsonl 資料資產 )
                                                                       │
                                                                       ▼
[模組三：基準測試]─>特徵：I/O-Bound─>方案：Asyncio(非同步事件迴圈)─>突破外部 API 頻寬限制
```

### 運算特徵對比矩陣

|**維度**|**模組二：Data Curation**|**模組三：Async Evaluation**|
|---|---|---|
|**瓶頸來源**|**CPU-Bound（計算密集型）**<br><br>  <br><br>海量文本的 Regex 正規表示式比對、純手寫 MinHash 簽名矩陣運算與雜湊分桶。|**I/O-Bound（網路/傳輸密集型）**<br><br>  <br><br>等待外部遠端 LLM-as-a-Judge 評分 API 回傳、本地檔案系統指標讀寫。|
|**並行機制**|**`multiprocessing.Pool` (多進程)**<br><br>  <br><br>繞過 Python GIL 限制，將任務分發至獨立的 OS 核心。|**`asyncio` + `aiohttp`/`openai` (非同步事件迴圈)**<br><br>  <br><br>單執行緒協程切換，在等待網路 I/O 回傳的空檔處理其他請求。|
|**併發規模**|嚴格受限於**硬體實體核心數**（如 M4 Pro 的 12 核心）。超過核心數會導致嚴重的進程切換開銷。|理論上可達 **Hundreds/Thousands 併發**，上限取決於外部 API 的 Rate Limits (RPM/TPM) 與核心 socket 緩衝區。|
|**序列化損耗**|**極高**。需嚴格遵守 `IPC` 無狀態傳遞（僅傳遞原生輕量元組，避免 pickle 阻礙效能）。|**極低**。協程間共享同一個進程內存，無須經過處理器層級的序列化。|

## 🔄 2. 資料資產狀態機與儲存落盤規範 (Data Contract)

為了確保模組二與模組三高度解耦，兩個模組**絕不共享內存物件**。模組二產出的乾淨語料必須進行「結構化落盤」，作為模組三的唯讀輸入（Read-Only Input）。

### 資料流轉生命週期

```
[ 原始髒亂語料 ] 
       │ （run_curation.py / DataCurationPipeline）
       ▼
[ 狀態：CLEANED_UNIQUE ] ──> 儲存至 data/curated/dataset.jsonl (每行獨立 JSON)
       │
       ├─> 核心欄位：id, text (清洗後標準化文本)
       │
       ▼ (進行微調訓練 / 模擬微調前後輸出)
[ 狀態：GENERATED_EVAL ] ──> 儲存至 data/eval/eval_cases.jsonl
       │
       └─> 核心欄位：id, prompt, baseline_response, finetuned_response
```

### 模組三輸入契約規範 (`eval_cases.jsonl` 範例)

每一行必須是一個合法的 JSON 物件，以便流式載入，避免記憶體擠爆：

JSON

```
{"id": "case_001", "prompt": "請解釋什麼是原子性...", "baseline_response": "原始模型回答的內容...", "finetuned_response": "微調模型回答的內容..."}
```

## 🛡️ 3. 模組三「非同步評估引擎」設計防禦焦點 (Pre-flight Checklist)

在開始編寫模組三代碼前，基於架構師視角，必須將以下邊界防禦機制寫入 TDD 設計藍圖中，拒絕脆弱的 `async` 盲目呼叫：

- **流量看門狗（Rate Limiter / Semaphore）：**
    
    外部大模型 API 均有嚴格的 TPM (Tokens Per Minute) / RPM (Requests Per Minute) 限制。模組三必須實作 `asyncio.Semaphore(max_concurrent_tasks)` 控制最大瞬間併發，組態必須由模組一注入。
    
- **指數退避重試（Exponential Backoff with Jitter）：**
    
    網路高併發環境下必現 `429 Too Many Requests` 或 `503 Service Unavailable`。評估引擎必須整合非同步重試機制（如 `tenacity` 非同步套件），在發生異常時進行步進式延時重試，並加入隨機抖動（Jitter）避免驚群效應。
    
- **裁判輸出強型態校驗（LLM-as-a-Judge Rubric Enforcement）：**
    
    評分模型（如 GPT-4 / Claude）回傳的文字具有不確定性。必須設計嚴格的 Prompt Rubric（1-5分），並強制要求模型以 JSON 格式回傳評分與理由。模組三需利用 Pydantic 進行非同步回傳值校驗，若格式崩潰需有降級（Fallback）或重新解析機制。
