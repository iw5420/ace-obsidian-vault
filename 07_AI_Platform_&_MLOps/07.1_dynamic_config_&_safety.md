
# 📂 7.1 Dynamic Configuration & Safety (動態配置與安全防護)

> 💡 **給 Python 入門者的導讀：**
> 
> 歡迎來到大模型（LLM）工程的世界！這份筆記會把我們在「模組一」中寫的複雜程式碼，拆解成連初學者都能秒懂的現實生活比喻。我們會弄清楚：為什麼程式要去查你的 Mac 電腦有幾核心？LoRA 到底是什麼神奇的技術？為什麼亂填參數會被程式當場抓包？

## 🧭 1. 概念核心：模組一獲取到的硬體資訊，對 LLM 有什麼用？

在執行大模型（LLM）微調或推理時，程式第一步會自動去向你的 Mac 作業系統「探聽」兩件事：

1. **`device: MPS`** （這台電腦有沒有蘋果專屬的顯示卡加速器？）
    
2. **`Physical Cores: 12`** （這台電腦擁有多少個真正的「高效能運算核心」？）
    

### ❓ 這對 LLM 有什麼幫助？

大模型在運算時，骨子裡其實是在做**海量的數學矩陣乘法**（幾十億甚至上百億次）。如果程式盲目地直接開始計算，就像是開一家工廠卻不知道自己有多少員工、有沒有自動化設備一樣，會導致嚴重的效率災難。

透過動態獲取這些資訊，程式能做到：

- **自動開加速器：** 偵測到 `MPS` 代表能直接把算術題丟給 M4 Pro 的強力 GPU（圖形處理器）去跑，速度比用老實的 CPU 快上數十倍。
    
- **精確分配工作：** 知道有多少「有效核心」後，就能精準安排同時計算的線程，不浪費任何一絲硬體效能。
    

## 🧵 2. 執行緒（Thread）大白話：多少 Thread 對 LLM 執行有什麼幫助？

### 🧑‍🍳 用「廚房備料」來聽懂 Thread

- **物理核心（Physical Cores）：** 廚房裡真正雇用的「專業主廚」人數（在你的 M4 Pro 上是 12 位）。
    
- **Thread（執行緒）：** 每個主廚手上同時在處理的「工作流」。
    
- **os.cpu_count() 的效能陷阱：** 蘋果晶片為了省電，除了專業主廚（P-core 效能核心）外，還塞了幾個負責滑手機、發呆的「實習生」（E-core 節能核心）。如果你用 Python 預設的 `os.cpu_count()`，它會把實習生也算進來（回報更高數值），結果把高難度的大模型矩陣運算分給實習生做，反而拖慢整間廚房的速度！
    

### 🎯 執行緒鎖定（torch.set_num_threads）的工業價值

我們的程式利用 `psutil` 繞過了實習生，精確算出了 **12** 個專業主廚（物理核心），並將 `torch.set_num_threads` 鎖死在 **12**。

- **好處 1：防止搶工作（減少 Context Switch 損耗）**
    
    如果開太多執行緒（例如開了 24 個），12 個主廚就會在多個工作之間切換來切換去（一下洗菜、一下切肉），光是切換就累死了。鎖定 12 個，就是讓 12 位主廚一人專心盯一個工作流，效率最高！
    
- **好處 2：防止電腦假死**
    
    在無加速晶片的保底模式下，程式會故意「留一手」（物理核心數 - 1），空出一個核心不參與運算。這樣可以確保你在跑大模型微調時，你的 Mac 畫面不會整個卡死，你還能一邊順暢地聽音樂或查資料。
    

## 🔬 3. 頂級企業底層技術調度解密 (Production-Grade Optimization)

除了生動的比喻，以下是我們在程式碼中針對不同硬體環境實作的「核心調配邏輯」。我們特別針對「顯卡（GPU）」和「核心」來拆解：

### 🍏 ① MPS 是什麼？它跟「顯卡」有什麼關係？

- **名詞大白話：** **MPS**（Metal Performance Shaders）就是**蘋果晶片（Apple Silicon）專用的「顯示卡加速驅動引擎」**。
    
- **做什麼用：** 如果把大模型運算比喻成一場賽車比賽，你的 **M4 Pro 晶片裡面的強力顯卡（GPU）** 就是那台時速 300 公里的賽車，而 **MPS 就是最頂級的專業賽車手**。當程式回報 `MPS Available: True`，就代表賽車手已經坐進車內、引擎發動，準備調用顯卡算力，用快上數十倍的速度狂飆大模型運算！
    
- **物理核心（Thread）在這裡的腳色：** 雖然主要是用顯卡（GPU）在算模型，但顯卡自己不會動，它需要 CPU 核心在旁邊當「副駕駛」，負責遞資料、指引路線（也就是 Dataloader 資料分發）。
    

#### 🚨 這裡隱藏的「效能陷阱」與「木桶效應」：

- **問題：** 蘋果晶片為了省電，把副駕駛分成了「專業主廚（P-core 效能核心）」與「滑手機實習生（E-core 節能核心）」。如果你直接呼叫 Python 內建的 `os.cpu_count()`，系統會把實習生也算進來，叫實習生去幫顯卡賽車手遞資料。
    
- **慘劇（木桶效應）：** 實習生動作太慢、手忙腳亂（這叫 Context Switch 上下文切換損耗），導致時速 300 公里的顯卡賽車，被迫停在路邊等實習生趕上來。這就是「木桶效應」——整體的最高速度，取決於最慢的那塊木板。
    
- **最佳化解法：** 我們的程式透過 `psutil.cpu_count(logical=False)` **強制在分派模型任務時排除實習生**（但背景的系統雜事依然會留給實習生維持），只留下 12 位專業主廚核心，把執行緒（`torch.set_num_threads`）緊緊錨定在 12。讓最強的副駕駛，完美配合最強的 M4 Pro 顯卡，把每瓦效能榨到極致！
    

### 🚀 ② CUDA (NVIDIA 環境)

- **大白話：** 如果換成插了 NVIDIA 顯示卡的電腦，**CUDA 就是黃仁勳家的「專屬賽車手」**。
    
- **最佳化解法：** 因為 NVIDIA 顯卡的胃口極大、吞吐量極高，為了不讓顯卡餓到，CPU 必須瘋狂超載工作。所以我們會配置高達 **[ 2 * 物理核心數 ]** 的線程，等於安排雙倍的副駕駛拚命把資料塞給 NVIDIA 顯卡加速器。
    

### ⚙️ ③ CPU (完全沒有顯卡加速的保底模式)

- **大白話：** 萬一這台電腦既沒有蘋果晶片、也沒有 NVIDIA 顯卡（`MPS` 和 `CUDA` 都是 `False`），那就代表**沒有賽車可用，只能靠 CPU 兩條腿自己跑馬拉松**。
    
- **最佳化解法：** 這時 CPU 算力會被 100% 榨乾。為了防止電腦因為算大模型直接當機（滑鼠卡住、畫面假死），我們會故意「留一手」**[ 物理核心數 - 1 ]**，強制空出一個核心去維持作業系統背景運作，確保你還能順暢動滑鼠或關掉程式。
    

## 🎨 4. 微調核心技術：LoRA 是什麼？Rank 與 Alpha 在幹嘛？

### 📚 用「修改教科書」來聽懂 LoRA

想像大模型（如 Llama 或 Mistral）是一本 **10,000 頁的超厚法律教科書**。今天你想讓它學會處理你們公司的「內部合約微調」，你該怎麼做？

- **傳統方法（全參數微調）：** 把 10,000 頁全部重新塗改、重新背誦。這需要極其恐怖的算力，你的 Mac 會直接記憶體爆炸。
    
- **LoRA（Low-Rank Adaptation）技術：** 完全不准動那本 10,000 頁的課本！只在課本後面**黏上幾頁乾淨的「便利貼」**。大模型看書時，一邊看原本的內容，一邊看便利貼上的補充。這樣你只要訓練那幾頁便利貼就好，省下 99% 的時間與空間！
    

### 🔢 參數大拆解：Rank ($r$) 與 Alpha ($\alpha$)

在配置檔案 `ryan_lora.yaml` 中，有兩個控制便利貼大小與字體大小的關鍵數字：

#### ① Rank ($r=8$) —— 便利貼的寬度（容量）

- **技術意思：** 低秩矩陣的階數（Rank）。
    
- **大白話：** **便利貼的格子有多少、能記多少新知識。**
    
- **設定學問：** 數字越大（如 16, 32），便利貼越寬，能學的複雜新知識就越多；但相對地，Mac 要花更多記憶體去算它。在頂級企業的通用規範中，這個數字**必須是 2 的冪次方**（2, 4, 8, 16...），因為計算機在做矩陣切塊時，2 的冪次方能剛好對齊硬體記憶體，跑起來速度最快。
    

#### ② Alpha ($\alpha=16$) —— 麥克筆的粗細（放大權重）

- **技術意思：** LoRA 的縮放因子常數（Scaling Factor）。
    
- **大白話：** **便利貼上的字，要用多大聲的音量（權重）喊給大模型聽。**
    
- **運作公式：** 系統底層調整參數時，實際生效的影響力比例是 $\alpha$ 除以 $r$。在我們設定 $r=8, \alpha=16$ 的狀況下，放大倍率就是 $16 / 8 = 2$ 倍。
    
- **設定學問：** 調整 $\alpha$ 可以讓你在不改變便利貼大小（Rank）的前提下，自由控制新知識對大模型的「影響強度」。如果 $\alpha$ 調太大，大模型會過度瘋狂依賴便利貼，忘記原本課本的基礎知識（這叫過擬合）；調太小，大模型就當作沒看見便利貼。
    

## 🛡️ 5. 型態防禦（Pydantic v2）：為什麼填錯參數會被當場攔截？

在 `schema.py` 程式碼中，我們放了幾道「嚴格的安檢閘門（field_validator）」：

- **當你把 Rank ($r$) 填成 `7`：** 安檢閘門一看：「7 不是 2 的 2 次方或 3 次方，不符合硬體對齊規範！」當場噴出錯誤並終止程式。
    
- **當你把學習率（lr）填成 `0.5`（太高了，模型會直接算到發狂）：** 安檢閘門立刻攔截：「學習率超出安全邊界 [1e-6, 1e-2]！」拒絕執行。
    

### 💡 這種「強型態防禦」的現實用處

如果沒有這套防禦系統，程式會帶著錯誤的參數 `7` 或 `0.5` 直接開始跑。等到大模型加載完畢（可能花了 10 分鐘）、開始執行第一步矩陣計算時，才會因為尺寸對不上而「轟然崩潰」，或者訓練了 3 個小時才發現模型吐出來的全部儲存值都是亂碼（NaN，梯度爆炸）。

透過 Pydantic v2，我們在**啟動後的第 0.1 秒**，就把所有粗心填錯的參數直接擋在門外，這就是工業級 MLOps 專案追求的**極致安全與高可靠性**。

## 🎯 6. 模組一：核心觀念大對齊 (Architectural Digest)

為了讓未來複習或任何 Python 入門者能秒懂，我們用「工廠」、「賽車」與「便利貼」來建立最精確的底層思維：

- **核心（Cores）與執行緒（Threads）：**
    
    - **核心**就是工廠裡真正雇用的「專業主廚人數」（M4 Pro 為 12 位）。
        
    - 執行緒（Thread）則是主廚手上正在盯著的「工作任務條」。
        
    - **鎖定核心數的實質意義：** 絕非防止員工偷懶，而是「防止主廚分心」！如果工作條開太多，主廚會一下洗菜、一下切肉，光是頻繁切換工作（Context Switch）就會累死、拖慢速度。鎖定在 12，就是讓 12 位主廚一人盯死一條生產線，效率最高。
        
- **異質硬體與賽車手（MPS / CUDA / CPU）：**
    
    - **MPS** 是蘋果晶片（Apple Silicon）專屬的**顯示卡（GPU）加速驅動引擎**。大模型運算就像賽車，M4 Pro 的強力 GPU 是賽車，而 **MPS 就是頂級賽車手**，負責開顯卡全力狂飆。
        
    - **CUDA** 則是 NVIDIA 陣營的專屬賽車手，因為 NVIDIA 顯卡胃口更大，所以可以透過 **2 倍超配** CPU 執行緒來拚命把資料塞給顯卡處理。
        
    - **CPU 模式** 則是既沒有跑車、也沒有車手，只能靠 CPU **兩條腿自己在路上跑馬拉松**的保底模式，速度極慢且容易讓整台 Mac 假死。
        
- **大模型微調技術（LoRA）：**
    
    - 大模型本身就像一本上萬頁的超厚法律教科書。**LoRA 不是尋找資訊的「索引」，而是黏在課本後面的「高效便利貼」**。
        
    - 我們不花恐怖算力去塗改整本教科書（全參數微調），而是只把新知識、新規則寫在便利貼上（LoRA 微調），省下 99% 的時間與空間。
        
    - **Rank（$r$）是便利貼的寬度（容量）：** 決定便利貼能記多少新東西。頂級企業規範**必須是 2 的冪次方**（2, 4, 8, 16...）以完美對齊計算機記憶體切塊，速度最快。
        
    - **Alpha（$\alpha$）是麥克筆的粗細（放大權重）：** 決定新知識對模型的影響強度。這兩個參數都必須通過 **Pydantic v2 安檢閘門** 的嚴格校驗，在啟動第 0.1 秒就阻斷任何填錯的數值，保障工業級系統的絕對型態安全。
