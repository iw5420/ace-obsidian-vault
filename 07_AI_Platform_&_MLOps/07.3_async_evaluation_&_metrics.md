## 🎯 1. 核心大會考：這條管線到底在「比較什麼」？

本章節與核心程式碼的真正重心，是在做一場**大模型微調前後的能力大對決**。簡單來說，系統是在比較：**「原始舊模型（Baseline）寫的答案」** 與 **「微調後新模型（Fine-tuned）寫的答案」** 到底誰更好？

為了終結盲測，我們引入了第三方公正標準，也就是「專家親手寫的黃金標準答案（Target / Ground Truth）」。整套引擎的評測閉環可以拆解為以下兩大階段：

### 📊 階段一：前面撈了什麼去做統計數？（數據平面）

在基準測試啟動時，主程式會加載評估資料集（Dataset）。每一筆被撈出來的核心數據（Case）都必須完整對齊以下 **4 個核心元素**，這也是前面計算 ROUGE/BLEU 統計指標的靈魂來源：

- **`prompt` (使用者提示詞)**：考卷上的題目（例如：「寫一段 Python 實作二元搜尋演算法」）。
    
- **`target_response` (黃金標準答案)**：領域專家或架構師親手寫好、絕對正確的「絕對座標軸（Reference）」。
    
- **`baseline_response` (原始模型回答)**：微調之前，未經優化的舊模型所寫出的原始答案。
    
- **`finetuned_response` (微調模型回答)**：微調之後，我們希望它變聰明的新模型所寫出的優化答案。
    

#### 傳統統計指標（ROUGE / BLEU）的數學比對：

- **原始模型的統計指標：** 計算 `baseline_response` 與 `target_response` 的字詞物理重合度。
    
- **微調模型的統計指標：** 計算 `finetuned_response` 與 `target_response` 的字詞物理重合度。
    
* **[ROUGE&BLEU ](./ROUGE&BLEU.md)** 
### 🤖 階段二：後面呼叫外部 AI 評分，在評什麼？（控制平面）

既然前面有了統計指標，為什麼後面還要呼叫外部 AI（`AsyncLLMJudge`）當閱卷老師？因為**傳統統計指標不懂人話，只能抓字面的硬性重合**。如果微調模型寫了一段邏輯完美、但換了全新同義詞的答案，統計指標會因為字詞沒對上而給出低分。

因此，後半段的控制邏輯是將數據打包送給外部裁判模型：

- 裁判**不參與**前面的 ROUGE/BLEU 數學計算。
    
- 裁判拿到的是題目（Prompt）、舊答案（Baseline）、新答案（Fine-tuned）。
    
- 裁判依據我們顯式宣告的評分量表（Rubric Prompt），進行軟性的**語意理解與邏輯審查**，給出 1 到 5 分並吐出客觀的判分理由。

讀者在看懂代碼前，必須先明白：**未來模型上線後，這套格式要怎麼整理？** 在現實世界的自動化大模型運維維運（LLMOps）中，這套資料架構的收集與聯動路徑如下：

                                │
                                ▼

## 📦 3. `_evaluate_case_stream` 終極數據結構硬核拆解

在非同步串流評估函式 `_evaluate_case_stream` 的最末端，這個 `return` 的字典（Dictionary）結構，本質上就是這筆測試案例的「終極數位成績單」：

Python

```
return {
    "id": case_id,                                # 1. 案例唯一識別碼
    "prompt": prompt,                            # 2. 測試題目
    "base_metrics": base_metrics,                # 3. 原始模型「硬指標」數據流
    "ft_metrics": ft_metrics,                    # 4. 微調模型「硬指標」數據流
    "judge_baseline_score": judge_base["score"],  # 5. 舊答案「軟指標」裁判分數
    "judge_baseline_reason": judge_base["reason"],# 6. 舊答案裁判判分理由
    "judge_finetuned_score": judge_ft["score"],  # 7. 新答案「軟指標」裁判分數
    "judge_finetuned_reason": judge_ft["reason"],# 8. 新答案裁判判分理由
}
```

### 📋 欄位實體含意與底層數據型態

#### ① `id` 與 `prompt`

- **資料型態：** `str`
    
- **說明：** 本筆測試案例的 ID 與考卷題目。用來在後續產出報表時進行分組（例如：`### 📋 案例識別碼: case_001`）。
    

#### ② `base_metrics` (原始模型獨立指標流)

- **資料型態：** `Dict[str, float]`
    
- **說明：** 這是原始舊模型（Baseline）**寫的答案跟**專家標答（Target）進行物理重合度比對後的純數學計分卡。
    

#### ③ `ft_metrics` (微調模型獨立指標流)

- **資料型態：** `Dict[str, float]`
    
- **說明：** 這是微調後新模型（Fine-tuned）**寫的答案跟**專家標答（Target）比對後的純數學計分卡。
    
- **架構價值：** 將其拆分為獨立雙流，我們才能拿 `ft_metrics` 的分數去減掉 `base_metrics` 的分數，進而算出現實生產環境中最珍貴的 **「微調淨提升能力值（Delta Δ）」**。
    

#### ④ `judge_baseline_score` 與 `judge_baseline_reason`

- **資料型態：** `int` (1 到 5 分) / `str`
    
- **說明：** 呼叫外部 AI 裁判後，閱卷老師給**舊模型答案**打的軟性語意分數與具體評語。
    

#### ⑤ `judge_finetuned_score` 與 `judge_finetuned_reason`

- **資料型態：** `int` (1 到 5 分) / `str`
    
- **說明：** 閱卷老師給**微調後新模型答案**打的軟性語意分數與具體評語。
    

## 🧭 4. 概念核心：關鍵名詞大通解（配合老實人舉例）

為了讓你在架構思維上徹底通透，我們將這條評估管線涉及的核心技術，用最生活化的老實人比喻拆解出來：

### ① 傳統統計相似度指標 (ROUGE / BLEU)

- **硬核定義：** 基於 Token-level 物理重合度的字串度量演算法。`ROUGE` 主要關注召回率（Recall，專家寫的字模型抓到了多少），常用於摘要與代碼生成；`BLEU` 主要關注準確率（Precision，模型寫的字有多少是精確的），常用於翻譯與對話。
    
- **老實人舉例：** 就像考英文聽寫時的「關鍵字對答案」。簡言之，只要模型的回答裡包含了專家標準答案裡的關鍵單字，統計指標就會飆高。它的優點是計算速度快到不可思議（純數學矩陣比對），缺點是死板、完全不懂人話（換個同義詞它就認不出來了）。
    

### ② 大模型裁判 (LLM-as-a-Judge)

- **硬核定義：** 利用具備高階推理能力的大型語言模型作為虛擬裁判，依據顯式宣告的評分量表（Rubric Prompt），對待評估文本進行盲測打分。
    
- **老實人舉例：** 就像作文考試裡的「閱卷老師」。當統計指標（聽寫對答案）因為模型換了個同義詞而給出 0 分時，大模型裁判能讀懂整段話的邏輯與深度，並依據 1 到 5 分的嚴格標準給出具體的人性化判分理由。
    

### ③ 非同步協程與 1.0 秒 / 1.5 秒雙層序列化控流防禦

- **硬核定義：** 利用 Python 協程機制達成單執行緒非阻塞 I/O 通訊，在外層迴圈與內層 API 調用上，強制使用 `await asyncio.sleep()` 進行物理延遲。
    
- **老實人舉例：** 就像遊樂園熱門設施的「排隊限流閘門」。即使外面有一萬個人想同時衝進去（幾萬筆評估數據），閘門一次只放行一個人，且每個人進去後必須停頓冷卻，確保外部 API 永遠維持在安全的降壓水位。
    

### ④ 強型態回傳防禦閘門 (Pydantic Response Schema)

- **硬核定義：** 在接收到遠端 API 回傳的非結構化 JSON 字串時，強制通過強型態 Schema 進行 Runtime 結構與值域校驗，不合規當場攔截。
    
- **老實人舉例：** 就像高鐵站的「自動驗票閘門」。我們要求裁判模型必須回傳包含 `score`（分數，且必須在 1 到 5 之間）與 `reason`（理由）的標準 JSON 格式。如果裁判模型亂講話、吐出 Markdown 的包裹標記（如 ```json）或是漏了欄位，閘門會當場抓出並啟動降級機制（給予安全降級分 1 分），絕對不讓髒數據導致整條自動化主管道崩潰死鎖。
