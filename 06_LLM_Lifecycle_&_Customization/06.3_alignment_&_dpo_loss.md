# 🏛️ 06.3 手寫 DPO 損失函數與偏好對齊管線

> **架構導讀**：
> 
> 本模組的核心任務是擺脫重型框架（如 TRL），直接使用純 PyTorch 張量算子（Tensor Ops）實作 **DPO (Direct Preference Optimization) 偏好對齊損失函數**。
> 
> 整個管線的運作重心在於：**建立一條「隱式偏好獎懲輸送帶」**。透過交叉比對「微調策略模型（Policy）」與「常駐基準模型（Reference）」對於成對語料（Chosen / Rejected）的累積對數機率，計算出淨優化偏好差（Delta Reward），藉此產生精確的梯度來更新 LoRA 權重。其最終目的，是為了讓模型在極短的步驟內快速收斂，主動親近好答案、排斥壞答案，在低算力成本下完成模型行為的對齊閉環。

## 🧭 1. DPO 核心架構與記憶體防禦機制

傳統的 RLHF（基於人類回饋的強化學習）需要同時載入 4 個模型（Policy, Reference, Reward, Value），這對本地端開發會造成嚴重的顯示記憶體（VRAM）斷崖式崩潰。

DPO 透過數學推導，將獎勵模型（Reward Model）隱式地代換為 Policy 模型與 Reference 模型的機率比值，因此在架構上只需要**雙軌模型**：

```
                    ┌─────────────────┐
                    │  Input Prompt   │
                    └────────┬────────┘
                             │ (共享同一個輸入向量，消除資料噪音)
            ┌────────────────┴────────────────┐
            ▼                                 ▼
   ┌─────────────────┐               ┌─────────────────┐
   │  Policy Model   │               │ Reference Model │
   │ (LoRA 參數可變動) │               │ (requires_grad  │
   │                 │               │  = False 凍結)  │
   └────────┬────────┘               └────────┬────────┘
            │                                 │
            ▼                                 ▼
   policy_logits [B, S, V]           ref_logits [B, S, V]
```

### 關鍵防禦機制：

1. **共享 Prompt 特徵平面**：Chosen 與 Rejected 數據在輸入端強制共享相同的 Prompt 特徵，防止因為 Prompt 向量差異導致優化器梯度方向被污染。
    
2. **生命週期鎖死**：Reference 模型在初始化時必須明確宣告 `requires_grad=False`。在訓練迴圈中，它只參與前向傳播（Forward Pass）以提供基準對數機率，不參與反向傳播，藉此釋放 50% 的梯度記憶體頻寬。
    

## 🧠 2. 核心算子與記憶體定址細節 (Token-Space Operations)

在實作 DPO 損失函數時，有兩個關鍵的 PyTorch 算子直接決定了矩陣運算的成敗：

### ① `gather` 算子（累積對數機率榨取）

DPO 的底層需要計算某個序列的「累積對數機率」（Log Likelihood）。這需要透過 `F.log_softmax` 與 `torch.gather` 配合完成。

### ② `scatter` 算子（非下底線 Out-of-place 模式，硬體相容防禦）

在自適應 Token 防禦或 Mock 矩陣測試中，若需要對特定位置的 Logits 強行覆寫賦值（例如將真實標籤位置灌入固定分值 `8.0`），必須嚴格禁止使用帶有下底線的 Inplace 算子（如 `.scatter_()`）。

- **硬體執行期限制（Runtime Constraint）**：Apple Silicon (MPS) 在執行前向傳播時，中間節點的記憶體定址是由 Metal 框架動態優化的。如果直接在原地（Inplace）強行修改未來需要追蹤梯度的張量數值，會因為找不到固定的實體快取緩衝區（Buffer）而引發核心定址錯誤（RuntimeError）。
    
- **正確做法**：使用不帶下底線的 `.scatter()`（Out-of-place）。這會迫使系統在 Unified Memory 中重新開闢一塊乾淨的緩衝區來承接計算結果，確保跨平台（MPS/CUDA）的硬體自適應安全。
    

## ⚙️ 3. DPO 損失函數矩陣運算與流水線流程圖

本模組的核心運算（`DirectPreferenceLoss`）完全使用純 PyTorch 底層張量算子推動。以下為單次前向傳播（Forward Pass）與損失值計算的完整流水線流程與維度（Shape）演變軌跡：

### 核心計算流（以單一模型提取對數機率為例）

```
[輸入 Logits 矩陣] ──> [Batch_Size, Seq_Len, Vocab_Size]
        │
        ▼ (實施 F.log_softmax(dim=-1) 進行詞彙軸歸一化)
[歸一化機率矩陣] ──> [Batch_Size, Seq_Len, Vocab_Size]
        │
        ├──────────────────────────────────────┐ (利用矩陣下標對齊)
        ▼ (將 Labels 擴展維度為 [B, S, 1])          │
[擴展標籤矩陣] ───> [Batch_Size, Seq_Len, 1]           │
        │                                      │
        └─────────────────┬────────────────────┘
                          ▼ (執行 torch.gather(dim=-1) 點對點榨取)
                 [Token級別對數機率] ──> [Batch_Size, Seq_Len, 1]
                          │
                          ▼ (.squeeze(-1) 降維並在序列軸 .sum(dim=-1) 降維加總)
                 [序列累積對數機率] ──> [Batch_Size] 核心回傳值
```

### 雙軌交叉人類偏好獎懲流水線

```
                       ┌────────────────────────────────────────┐
                       │  4 組累積對數機率 (維度皆為 [Batch_Size])  │
                       └─┬──────────┬──────────┬──────────┬─────┘
                         │          │          │          │
                         ▼          ▼          ▼          ▼
                     Policy      Policy    Reference  Reference
                     Chosen     Rejected    Chosen    Rejected
                         │          │          │          │
                         └────┬─────┘          └────┬─────┘
                              │ (相減)               │ (相減)
                              ▼                     ▼
                        Policy偏好率           Ref偏好率
                              │                     │
                              └──────────┬──────────┘
                                         │ (Policy偏好率 - Ref偏好率) * Beta
                                         ▼
                                   隱式獎勵差矩陣 
                        Chosen_Rewards  與  Rejected_Rewards
                                         │
                                         ▼ (計算淨優化偏好差 Delta = Chosen - Rejected)
                                  Delta Reward 向量
                                         │
                                         ▼ (套入 -F.logsigmoid() 並取全域 .mean())
                                   [最終 DPO Loss 純量]
```

## 📈 4. 生產級觀測指標對齊表 (Production Metrics & Boundary)

在訓練環境（WandB / MLflow）中，我們不看黑盒子，只透過監控以下四個核心純量（Scalar）的邊界變化，來判定對齊管線是否健康：

|**觀測指標 (Metrics)**|**數值區間定義**|**數值為「大 / 正」的意思**|**數值為「小 / 負」的意思**|**業務含意與異常排查**|
|---|---|---|---|---|
|**`Loss`**|理論區間：`0` 到 $+\infty$<br><br>  <br><br>初始通常在 `0.69` 附近|**數值過大 (如 > 1.0)**：<br><br>  <br><br>代表模型正在「瘋狂困惑」，更新梯度過猛導致參數發散。|**數值極小 (如 < 0.1, 穩定趨近 0.04)**：<br><br>  <br><br>代表 Policy 模型的參數梯度正沿著優化器完美收斂，成功找到最優解。|**生產排查**：<br><br>  <br><br>若數值持久橫盤在 `0.69` 且不下滑，代表學習率（lr）過小，或 Chosen 與 Rejected 數據內容過於相似，模型分不出來。|
|**`Delta Reward`**<br><br>  <br><br>(淨優化偏好差)|理論區間：$-\infty$ 到 $+\infty$<br><br>  <br><br>核心分水嶺為 **`0`**|**大於 0 且持續衝高 (如 +12.10)**：<br><br>  <br><br>代表模型對 Chosen 的愛，遠大於對 Rejected 的愛。**對齊大獲成功**。|**小於 0 且持續下墜 (如 -17.50)**：<br><br>  <br><br>發生「偏好倒置」。代表模型越學越壞，竟然更喜歡人類討厭的垃圾答案。|**生產排查**：<br><br>  <br><br>此指標**必須恆為正數且步進上揚**。一旦跌入負數區，必須立即停機，檢查是否將資料集中的 chosen 與 rejected 標籤欄位給接反了。|
|**`Rewards/Chosen`**|理論區間：$-\infty$ 到 $+\infty$<br><br>  <br><br>隨訓練逐步拉高|**數值大 (正值越來越大)**：<br><br>  <br><br>代表當前 Policy 模型在講出符合人類偏好的 Chosen 答案時，其發言機率被正確頂高。|**數值小 (或負值絕對值變大)**：<br><br>  <br><br>代表模型對好答案的說話機率正在被壓抑，不符合業務預期。|**生產排查**：<br><br>  <br><br>搭配下面一欄看。DPO 的精髓是拉開相對差距，只要 Chosen 的數值增長速度大於 Rejected，對齊就依然在軌道上。|
|**`Rewards/Rejected`**|理論區間：$-\infty$ 到 $+\infty$<br><br>  <br><br>隨訓練逐步壓低|**數值大 (正值或高於Chosen)**：<br><br>  <br><br>代表模型對壞答案的偏好不降反升，參數正在向有毒樣本傾斜。|**數值小 (負值絕對值極大)**：<br><br>  <br><br>代表當前 Policy 模型在講出被拒絕的 Rejected 答案時，其發言機率正在遭受指數級的無情痛擊。|**生產排查**：<br><br>  <br><br>此指標的收斂曲線應該要像坐溜滑梯一樣下滑，證明模型的隱式懲罰力道正在持續加重。|

## 🎯 5. 大白話名詞破譯手冊 (小白也能懂的技術轉譯)

為了讓團隊其他成員或非本建模領域的工程師能快速上手，以下將本模組最晦澀的 6 個專有名詞，用最接地氣的生活例子進行破譯：

### ① DPO (Direct Preference Optimization，直接偏好優化)

- **大白話解釋**：**「沒有中間商賺差價的直接對齊法」**。
    
- **老實人舉例**：以前要教 AI 講禮貌（RLHF 傳統做法），要先請一位專業的「禮貌評分員」（Reward Model），AI 每講一句話，評分員就打分數，AI 再根據分數調整自己。這很麻煩，因為你要同時養 AI 還要養評分員。DPO 則是直接把評分員開除。我們直接塞給 AI 成對的考古題：「人家說謝謝，你回答不客氣（Chosen，讚）」和「人家說謝謝，你回答關我屁事（Rejected，爛）」。AI 左右對照，直接去拉高前者的發言機率、調低後者的機率。不立中間人，直接完成訓練。
    

### ② Policy Model (策略模型) 與 Reference Model (參考模型)

- **大白話解釋**：**「正在接受特訓的學生」與「凍結不准動的考古題標準答案」**。
    
- **老實人舉例**：Policy Model 就是目前在操場上狂奔、天天被梯度調整的「新 AI」。我們希望牠越來越符合人類胃口。Reference Model 則是出廠時的「老 AI」。DPO 怕新 AI 為了盲目討好人類（例如人類喜歡聽好聽話，AI 就開始瘋狂拍馬屁、講亂碼），會規定新 AI 不管怎麼變，都必須拿老 AI 當常駐錨點，發言的邏輯底線不能偏離老 AI 太遠。所以老 AI 在記憶體裡是完全被「鎖死、不准更新（requires_grad=False）」的。
    

### ③ LoRA (低秩適應度微調)

- **大白話解釋**：**「不改大樓主結構，只在外牆加裝一盞外掛電梯」**。
    
- **老實人舉例**：原本的大模型有數百億個參數，就像一棟蓋好的 100 層摩天大樓。如果要微調它，把所有牆壁敲掉重建（全參數微調），本地端的 Mac 記憶體會直接炸毀。LoRA 的做法是：把大樓的所有牆壁通通凍結，不准塗改。只在旁邊搭一個很輕量的小樓梯。訓練的時候，大模型只負責出死資料，我們只去更新這個小樓梯裡的極少數參數。既省記憶體，又能達到 95% 以上的微調效果。
    

### ④ Log_Softmax 歸一化

- **大白話解釋**：**「把全班的分數，換算成有對數保護的機率百分比，防止極端學霸作票」**。
    
- **老實人舉例**：大模型剛算出來的原始分數（Logits）可能很極端，有的字得 10000 分，有的得 -500 分，沒辦法直接比。`Softmax` 負責把這些亂七八糟的分數拉平，變成總和為 100% 的機率值（例如 A 字機率 70%、B 字機率 20%）。而前面加個 `Log（對數）`，是為了數學上的穩定性。因為機率相乘（0.7 * 0.2 * 0.1...）數字會越來越小、小到計算機崩潰；把機率取 Log 之後，「相乘」就變成了「相加」，矩陣運算只要做代數加總（.sum()）就能算完，效率極高。
    

### ⑤ Gather 算子

- **大白話解釋**：**「拿著點名簿，精準去教室裡把坐在特定位置的學生抓出來」**。
    
- **老實人舉例**：當大模型噴出 `[Batch_Size, Seq_Len, Vocab_Size]` 這麼龐大的三維矩陣時，它就像一個坐滿了幾萬個人的巨大電影院。但我們手裡其實有標準答案的標籤（Labels，也就是 Chosen 序列真正的 Token ID）。`torch.gather` 就像是一個精準的憲兵，他手裡拿著座位號碼，無視其他不相干的雜訊字，直接把目標 Token 對應的那個格子裡的對數機率值「點對點抽出來」組成一條乾淨的輸送帶，方便後續直接計算 DPO 損失。
    

### ⑥ Out-of-place 記憶體安全算子 (解耦硬體定址限制)

- **大白話解釋**：**「拿一張新白紙寫答案，不要在原本的考卷上用立可帶塗改」**。
    
- **老實人舉例**：在寫 PyTorch 時，`matrix.scatter_()`（帶下底線）叫做 Inplace（原地塗改）；`matrix.scatter()`（不帶下底線）叫做 Out-of-place（另覓新地）。Apple 的 M系列晶片（MPS）在幫深度學習矩陣算帳時，前向傳播算出來的中間數據在記憶體裡的位置隨時在動。如果你此時用「立可帶（Inplace）」強行在原地把數據抹掉改寫，晶片會因為找不到實體快取緩衝區而直接罷工閃退。我們改用 Out-of-place 算子，就是逼系統去旁邊開一塊新座位來放答案，全平台硬體就會 100% 綠燈通行。
    

## 🏁 6. 全模組總結：重心流程、產出結果與實際應用

為了對本模組建立全景式的工程架構認知，以下將此對齊管線的**執行重心、產出成果以及如何在實際業務中發揮價值**進行最終提煉：

### 🔄 ① 運作重心流程（The Core Process）

本模組的核心運作，本質上是一條**高解耦的雙軌矩陣代數輸送帶**。其運作重心可拆解為三個步驟：

1. **輸入端防禦與共享空間**：強制 Chosen（人類偏好）與 Rejected（人類反感）的語料在物理記憶體層面共享同一個 Prompt 輸入向量。
    
2. **雙軌模型並行提取**：一條軌道讓「接受微調的新模型 (Policy)」跑，另一條軌道讓「完全凍結的舊模型 (Reference)」跑，兩者同時輸出三維的 Logits 矩陣。
    
3. **點對點機率榨取**：不使用大型黑盒子框架，而是利用底層 `F.log_softmax` 鎖定詞彙軸分佈，隨即透過 `gather` 算子，依據標準答案的 Token ID，精確把成對語料的「累積對數機率」給抽點出來。
    

### 📦 ② 最終產出的結果（The Tangible Output）

透過上述流程的計算，本模組最終會產出：

- **DPO Loss 核心純量**：一個經過 `-F.logsigmoid()` 激活與全域平均（`.mean()`）處理後的單一損失值（Scalar）。
    
- **極高準確度的偏好梯度（Gradients）**：當新模型對好答案（Chosen）的偏好低於舊模型，或者對壞答案（Rejected）的發言機率不降反升時，此損失函數會**觸發指數級的數學懲罰**，產生一個強烈的反向梯度。
    

### 🚀 ③ 這項結果用來做什麼？（實際業務應用價值）

這個產出的 Loss 與梯度，在工程與業務層面有著至關重要的決定性用途：

1. **驅動 AdamW 優化器更新 LoRA 權重**：優化器會利用這個精確的偏好梯度，在每一次 Iteration 中，精準塗改外掛電梯（LoRA 矩陣）中的參數。
    
2. **拉開隱式獎勵斷層差距**：強制拉開新模型在面對「好答案」與「壞答案」時的說話機率。隨著訓練推進，模型講出正確、禮貌、符合業務規範語句的機率會步進上揚，而講出胡言亂語、有毒語料或死循環亂碼的機率則會被直接壓抑至底線。
    
3. **低成本落地生產級 AI Agent**：這項結果讓我們得以在不需要額外耗費 VRAM 養一個實體「獎勵模型（Reward Model）」的苛刻條件下，直接在單機（M4 Pro）環境下完成大模型的行為對齊閉環。這使得最終交付的 LLM 能夠在具體業務情境（如客服、財務分析、技術程式碼生成）中，**既具備專業知識，又完美符合人類的表達習慣與安全防護規範**。
